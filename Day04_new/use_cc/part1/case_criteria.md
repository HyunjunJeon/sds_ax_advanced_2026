# 내 사례 고르기: 조건 여섯 가지와 예시 사례 다섯 개

이 과정은 수강생이 **자기 업무 사례 하나**를 골라 Part 1부터 평가 실습까지 끝까지 끌고 갑니다.
Part 1에서는 그 사례의 능력을 설계하고, Part 2~5에서는 그 설계를 MCP 서버와 Skill로 만들고,
마지막 실습에서는 만든 것을 평가하고 고칩니다.

사례를 아무것이나 고르면 Part 4나 평가 실습에 가서 "내 사례에는 이게 없다"가 됩니다.
예를 들어 부작용이 있는 도구가 하나도 없으면 중복 실행을 실험할 수 없고, 막힐 만한 동작이 없으면 권한 거부를 실험할 수 없습니다.
아래 여섯 조건은 강사 사례(요구사항 인터뷰 서버)가 각 Part에서 실제로 쓰는 요소를 거꾸로 짚어서 만든 것입니다.
여섯 개를 모두 만족하는 사례를 고르세요.

## 1. 조건 여섯 가지

| 번호 | 조건 | 왜 필요한가 (쓰는 Part) | 강사 사례에서는 |
|---|---|---|---|
| C1 | **여러 단계에 걸친 상태**가 있다. 한 번의 도구 호출로 끝나지 않고, 앞 호출의 결과가 뒤 호출의 조건이 된다 | Part 3에서 상태 전이를 막는 곳을 정하고, Part 4에서 서버가 죽은 뒤 이어 가기(재개)를 실험한다 | 세션이 `draft` → `ready` → `frozen`으로 바뀐다 (`cap_lab/server/workflow.py:82`) |
| C2 | **부작용이 있는 도구**가 하나 이상 있다. 부르면 무언가가 새로 생기거나 바뀐다 | Part 4의 멱등성(같은 호출을 두 번 보내도 결과가 한 번과 같은가), 실습의 중복 실행 검사 | `save_evidence`는 파일을 만들고, `start_interview`는 부를 때마다 새 세션을 만든다 (`cap_lab/server/server.py:248-249`의 주석) |
| C3 | **권한이 거부될 만한 동작**이 하나 이상 있다. 실제 업무에서 "그건 당신이 할 수 없다"고 막힐 수 있는 일이다 | 실습의 권한 거부 검사(거부된 뒤 같은 호출을 되풀이하지 않는가) | 장애 주입으로 `save_evidence`를 거부한다 (`cap_lab/server/server.py:59`의 `FAULT_EXAMPLE`) |
| C4 | **판단이 필요한 지점**이 하나 있다. 정해진 값 비교가 아니라 문장의 뜻을 읽어야 정할 수 있는 곳이다 | Part 1에서 판단을 코드 규칙, 판단 모델(Jev), 생성(LLM) 중 어디에 둘지 정하고, Part 4에서 그 판단을 게이트로 만든다 | 완료 기준을 실행 결과로 확인할 수 있는가(testability) (`cap_lab/server/gate.py:28`) |
| C5 | **도구는 3~5개**다 | 수업 시간 안에 Claude Code와 함께 구현할 수 있는 크기다. 도구가 2개 이하면 도구 선택을 실험할 거리가 없고, 6개 이상이면 시간이 모자란다 | 7개(강사 사례는 미리 만들어 두었으므로 더 많다) |
| C6 | **가상 데이터와 로컬 저장소만** 쓴다. 실제 사내 시스템, 실제 고객 정보, 실제 계정에 연결하지 않는다 | 모든 Part. 아래 "C6을 꼭 지켜야 하는 이유"를 보라 | SQLite 파일과 근거 폴더의 JSON 파일만 쓴다 |

### C6을 꼭 지켜야 하는 이유

1. **입력이 외부로 전송됩니다.** Claude Code에게 하는 말, 도구의 입력과 출력은 Anthropic으로 갑니다.
   판단 모델(Jev)을 쓰면 판단할 문장이 Decision API 공급자에게 갑니다. 기록을 Langfuse에 남기면 프롬프트와 도구 입출력이 Langfuse로 갑니다.
   실제 업무 자료를 넣으면 그대로 밖으로 나갑니다.
2. **실습이 일부러 부작용을 일으킵니다.** Part 4와 평가 실습에서는 같은 도구를 두 번 보내 보고, 일부러 오류를 넣고, 권한 거부를 만듭니다.
   실제 시스템에 연결된 도구로 이것을 하면 실제 예약이 두 번 잡히거나 실제 발주가 두 번 나갑니다.
3. **실패를 마음 편히 관찰해야 합니다.** 이 과정은 실패를 숨기지 않고 드러내는 연습입니다. 실패가 진짜 피해로 이어지는 환경에서는 그 연습을 할 수 없습니다.

실제 업무를 흉내 내고 싶다면 그 업무의 **모양**(어떤 단계가 있고, 무엇이 막히고, 무엇을 판단하는가)만 가져오고,
데이터는 지어낸 이름과 숫자로 채운 SQLite 파일이나 JSON 파일로 만드세요.

## 2. 사례를 정하지 못했을 때: 예시 사례 다섯 개

아래는 모두 **가상 업무**입니다. 그대로 골라도 되고, 자기 업무에 맞게 바꿔도 됩니다.
다만 바꾼 뒤에도 C1~C6을 다시 확인하세요. 도구 이름은 예시일 뿐이고, 도구를 어떻게 나누고 이름을 무엇으로 할지는 Part 2에서 직접 정합니다.

### 예시 1. 사내 장비 반입 신청

외부 장비(노트북, 측정 장비)를 사옥에 들여오려면 신청하고 보안 담당자의 승인을 받아야 하는 업무입니다.

- 도구 예시: `create_request`(신청서 만들기), `add_device`(장비 추가), `submit_request`(제출), `approve_request`(승인), `get_request`(조회)
- 이 사례에서 판단이 필요한 곳: 신청서에 적힌 반입 사유가 규정상 허용되는 사유인가

### 예시 2. 장애 티켓 분류와 배정

모니터링 알림이나 사용자 신고로 들어온 장애 티켓의 심각도를 정하고 담당 팀에 배정하는 업무입니다.

- 도구 예시: `open_ticket`(티켓 만들기), `classify_ticket`(심각도 기록), `assign_ticket`(담당 팀 배정), `close_ticket`(종료), `get_ticket`(조회)
- 이 사례에서 판단이 필요한 곳: 신고 문장을 읽고 심각도(P1~P4)를 정하는 일

### 예시 3. 월간 보고서 초안과 게시

팀의 월간 실적 보고서 초안을 만들고, 검토를 거쳐 사내 게시판에 올리는 업무입니다.

- 도구 예시: `create_draft`(초안 만들기), `update_section`(항목 고치기), `request_review`(검토 요청), `publish_report`(게시), `get_report`(조회)
- 이 사례에서 판단이 필요한 곳: 초안이 필수 항목을 모두 담았는가. 이 판단을 코드 규칙(필수 항목 제목이 있는지 세기)으로 둘지, 판단 모델(내용이 실제로 그 항목을 다루는지)로 둘지가 Part 1의 좋은 토론거리입니다

### 예시 4. 소모품 구매 요청

사무 소모품 구매를 요청하고, 승인되면 발주하는 업무입니다.

- 도구 예시: `create_order`(요청 만들기), `add_item`(품목 추가), `approve_order`(승인), `place_order`(발주), `get_order`(조회)
- 이 사례에서 판단이 필요한 곳: 요청한 품목이 소모품 규정에 해당하는 품목인가

### 예시 5. 코드 리뷰 요청 접수와 배정

변경 사항에 대한 리뷰 요청을 받아 리뷰어를 배정하고, 승인 여부를 기록하는 업무입니다.

- 도구 예시: `open_review`(요청 만들기), `assign_reviewer`(리뷰어 배정), `record_verdict`(승인·반려 기록), `merge_change`(병합), `get_review`(조회)
- 이 사례에서 판단이 필요한 곳: 변경 설명을 읽고 위험도를 정해 리뷰어를 몇 명 붙일지 정하는 일

### 예시 사례가 조건을 만족하는지

| 예시 | C1 여러 단계 상태 | C2 부작용 도구 | C3 거부될 만한 동작 | C4 판단 지점 | C5 도구 수 | C6 가상·로컬 |
|---|---|---|---|---|---|---|
| 1. 장비 반입 신청 | 작성 → 제출 → 승인 | `submit_request`, `approve_request` | 보안 담당자가 아닌 사람의 `approve_request` | 반입 사유가 허용 사유인가 | 5 | 가상 신청서, SQLite |
| 2. 장애 티켓 | 접수 → 분류 → 배정 → 종료 | `assign_ticket`(두 번 보내면 두 팀에 배정될 수 있다) | 당직자가 아닌 사람의 P1 배정 | 신고 문장의 심각도 | 5 | 가상 티켓, SQLite |
| 3. 월간 보고서 | 초안 → 검토 → 게시 | `publish_report`(두 번 보내면 두 번 게시될 수 있다) | 게시 권한이 없는 사람의 `publish_report` | 필수 항목을 다 담았는가 | 5 | 가상 실적 숫자, JSON 파일 |
| 4. 소모품 구매 | 요청 → 승인 → 발주 | `place_order`(두 번 보내면 두 번 발주될 수 있다) | 한도를 넘는 금액의 `approve_order` | 품목이 규정 품목인가 | 5 | 가상 품목표, SQLite |
| 5. 코드 리뷰 | 요청 → 배정 → 판정 → 병합 | `merge_change`, `assign_reviewer` | 승인 없이 `merge_change` | 변경의 위험도 | 5 | 가상 변경 설명, SQLite |

## 3. 내 사례가 조건을 만족하는지 확인하는 법

Part 1의 설계서(`design_sheet.md`) 2절에 이 표와 같은 칸이 있습니다. 칸마다 "있다/없다"만 적지 말고 **어디에 있는지**를 한 줄로 적으세요.
"부작용 도구: 있다"가 아니라 "부작용 도구: `place_order`. 부르면 발주 기록이 하나 생긴다"처럼 적습니다.
한 칸이라도 비면 사례를 조금 넓히거나 다른 사례를 고르세요. 비어 있는 칸은 뒤의 Part에서 실험할 거리가 없다는 뜻입니다.
