> 1절의 값은 저자가 2026-11-04에 녹화한 실제 기록(이하 "녹화본")에서 옮겼습니다. 녹화본은 강사가 갖고 있고 이 저장소에는 넣지 않았습니다. 그 녹화도 **1회 관찰**입니다.

## 0. 내 사례 한 줄

- 사례 이름: 요구사항 인터뷰 (새 업무의 목표, 제약, 완료 기준을 질문으로 모아 명세로 고정한다)
- 누가 이 능력을 쓰는가: 무언가를 만들고 싶은데 무엇을 정해야 하는지 아직 모르는 사람
- 고른 이유: 이 과정의 모든 Part를 한 사례로 보여 줄 수 있다. 상태, 부작용, 거부, 판단이 모두 들어 있다

## 1. 인터뷰 결과 (seed)

근거: 녹화본의 근거 폴더 `evidence/198b6ca2923941e4b051c663f50a4dab/`에 있던 `seed-eadb5a20fcad421293340c64d63b9080.json`,
판정 기록은 같은 폴더의 `event-00000003.json`. 내 실험 폴더의 `evidence/<서버 세션 ID>/`에도 같은 이름 규칙의 파일이 생깁니다.

| 칸 | 내용 |
|---|---|
| 서버 세션 ID | `198b6ca2923941e4b051c663f50a4dab` |
| goal (목표) | 우리 팀 비품 대여 현황을 한눈에 보여 주는 도구를 만들고 싶어요. |
| constraints (제약) | 대여 기록에 사람 이름 대신 사번만 남긴다. |
| acceptance_criteria (완료 기준) | 비품 20개와 대여 기록 50건을 넣으면 대여 중인 비품과 반납 예정일이 표 하나에 모두 나온다 |
| 서버가 완료 기준을 되물었는가 | 예 |
| 되물었다면 내가 처음 말한 완료 기준 | "완료 기준은 팀원들이 보기 편하면 완료예요." (Claude가 `record_answer`에 넣은 문장은 "팀원들이 보기 편하면 완료.") |
| 되물었다면 판정 점수와 문턱값 | `gate.score` 0.07, `gate.threshold` 0.5, `gate.source` `elicited` |

두 가지를 눈여겨볼 만합니다.

- **Claude는 사용자의 말을 조금 바꿔서 도구 인자로 넣었습니다.** 제약 "사번만 남기는 거예요"는 "사번만 남긴다."가 되었습니다. 내용은 같지만 문장은 생성(LLM)이 만든 것입니다. 목표 문장(goal)도 같은 방식으로 바뀔 수 있고, 그것을 막는 게이트가 07의 H2입니다.
- **서버가 사용자에게 직접 받은 완료 기준은 Claude가 보낸 인자에 나타나지 않습니다.** 그래서 녹화본 발화 3에서 Claude는 "서버에 저장된 내용이 제가 보낸 것과 다르다"며 확정을 멈추고 사용자에게 확인을 받았습니다(녹화본 발화 3의 마지막 답).

## 3. 능력의 네 요소

이 사례는 두 하네스에서 돌아갑니다. 노트북의 Deep Agent와 이 실습의 Claude Code입니다.
**MCP 서버와 SKILL.md는 두 하네스에 그대로 붙지만, 실행 제어와 상태 일부는 하네스마다 다릅니다.** 아래 표는 Claude Code 쪽입니다.

| 요소 | 무엇을 두는가 | 어디에 두는가 | 빠지면 어떻게 되는가 |
|---|---|---|---|
| 지침 | 인터뷰 순서, 답을 지어내지 말 것, 오류 코드별 행동 | 실험 폴더의 `.claude/skills/requirements-interview/SKILL.md`. description은 처음부터 실리고, 본문은 `Skill` 도구를 부를 때 대화에 들어온다 (녹화본 차례 1 다음의 "(지침)" 줄) | 도구는 그대로 남는다. 오류도 나지 않는다. 무엇이 달라지는지는 미션의 선택 깨뜨리기에서 직접 본다 |
| 도구 | MCP 도구 7개 | 실험 폴더의 `.mcp.json`이 띄우는 `cap_lab/server/server.py`. Claude Code의 내장 도구도 함께 있다(강사 기계의 녹화본에서 전체 35개 = 내장 28 + MCP 7) | 인터뷰를 시작할 수 없다. 서버가 뜨지 않으면 `/mcp`에 실패로 보인다 |
| 실행 제어 | 도구 사용 승인, hook, 도구 지연 공개 | 대화형 manual 모드에서는 MCP 도구마다 처음 쓸 때 승인을 묻는다. 녹화에서는 `--allowedTools mcp__requirements`로 미리 허용했다. MCP 도구는 이름만 처음부터 실리고 정의(인자 형식)는 필요할 때 불러온다(`/context`의 `loaded on-demand`). 녹화본에서는 `ToolSearch`로 정의를 불러온 뒤 불렀다(차례 2) | 승인을 거절하면 그 턴이 멈추고 도구는 실행되지 않는다. 지연 공개가 없으면 도구 정의가 처음부터 모두 문맥에 실린다 |
| 상태 | 업무 상태와 대화 상태 | 업무 상태는 서버의 SQLite와 근거 파일(실험 폴더의 `work/`, `evidence/`). 대화 상태는 Claude Code 세션 기록 `~/.claude/projects/<실험폴더-이름>/<세션 ID>.jsonl` | 근거 파일이 남아 있으면 서버가 업무 상태를 다시 만들 수 있다(Part 4). 세션 기록이 없으면 `--resume`으로 대화를 이어 갈 수 없다 |

세션 ID가 두 개라는 점에 주의하세요. 녹화본의 Claude Code 세션 ID는 `9b5c32ab-…`(대화)이고, 서버 세션 ID는 `198b6ca2…`(업무)입니다.

## 4. 판단은 어디에 두는가

| 무엇을 정하는가 | 입력은 무엇인가 | 판단 위치 | 그 위치로 둔 이유 |
|---|---|---|---|
| 확정해도 되는가 | 아직 답하지 않은 필수 항목 목록 | 코드 규칙 | 입력이 닫힌 집합(항목 이름)이다. 비어 있지 않으면 `seed_incomplete` (`cap_lab/server/workflow.py:222-227`) |
| 오류가 나면 다시 보낼까 | 오류 코드(`permission_denied`, `temporarily_unavailable` 등) | 코드 규칙 (지침 문장으로 적혀 있다) | 오류 코드는 닫힌 집합이고 행동이 표 하나로 정해진다 (`skills/requirements-interview/SKILL.md:41-47`) |
| 완료 기준을 실행 결과로 확인할 수 있는가 | 사용자가 말한 완료 기준 문장 | 판단 모델(Jev) | 뜻을 읽어야 하고, 결과를 세 단계 점수로 줄일 수 있다 (`cap_lab/server/gate.py:28`) |
| 다음 질문을 어떤 말로 건넬까 | 지금까지의 대화와 `next_question` | 생성(LLM) | 결과가 사람에게 보여 줄 문장 그 자체다 |

### 4.1 판단 모델(Jev)로 둔 판단

| 칸 | 내용 |
|---|---|
| 판단할 문장(입력) | `record_answer`로 들어온 완료 기준 문장 |
| 질문 모양 | `Score`(순서 있는 세 단계: 판정할 수 없다 / 일부만 판정할 수 있다 / 실행 결과로 참·거짓을 판정할 수 있다) (`cap_lab/server/gate.py:28-35`) |
| 결과를 무엇과 비교하는가 | 기댓값 `score`를 문턱값과 `>=`로 비교한다 (`cap_lab/server/gate.py:54`). 문턱값 0.5는 라벨로 재지 않은 자리값이다 |
| 문턱값을 잴 라벨 | 완료 기준 문장마다 "확인 가능/불가"를 사람이 붙인 표. 저자 쪽에서 준비하며 수업에서 읽지 않는다 |
| 판정기를 부를 수 없을 때 | 아무것도 기록하지 않고 `decision_unavailable`을 돌려준다(fail-closed) (`cap_lab/server/server.py:269-274`) |

## 5. 먼저 예측: 처음 어디서 실패할까

- [x] 판단해야 할 곳을 그냥 통과시킨다 (판단)

이유: 게이트를 끈 서버(`--gate off`)에서는 "보기 편하면 완료" 같은 모호한 완료 기준이 그대로 기록되고 확정까지 갈 수 있다.
노트북 과정의 저자 측정(Deep Agent, 게이트 끔)에서 첫 실패 20회 중 11회(S3)가 모호한 완료 기준을 그대로 확정한 것이었다 (`docs/DESIGN.md:234`, `:247`). 나머지 9회(S5)는 반대로 에이전트가 확정을 보류하고 다시 물은 경우다 (`docs/DESIGN.md:249`).
이 예측이 Claude Code에서도 맞는지는 평가 실습에서 다시 확인한다.

## 6. 확인 질문 (예시 답)

미션 카드의 확인 질문 1~5에 대한 강사 사례의 답입니다. 수강생은 자기 답을 먼저 쓴 뒤에 봅니다.

1. 지침은 `SKILL.md`, 도구는 MCP 서버의 도구 7개, 실행 제어는 도구 사용 승인과 지연 공개, 상태는 서버의 SQLite·근거 파일과 Claude Code 세션 기록이다. 지침(SKILL.md)을 빼면 오류 없이 인터뷰가 사라진다. 저자 1회 관찰(2026-11-04, Opus 5.5)에서 Claude Code는 도구를 불러올 수 있었는데도 부르지 않고 질문 목록을 글로만 답했고, 서버 세션도 근거 파일도 생기지 않았다. 노트북의 Deep Agent에서는 도구가 아예 보이지 않아서 못 썼다(01 노트북 3.4절). 증상은 같아도 원인이 하네스마다 다르다. Claude Code에서는 Skill이 도구를 여는 열쇠가 아니라 **도구를 쓸 이유**를 알려 주는 쪽이다.
2. 이름은 처음부터 있었고 정의(인자 형식)는 없었다(`/context`의 `loaded on-demand`). 녹화본에서는 차례 2의 `ToolSearch` 줄이 정의를 불러온 근거다. 저자의 다른 1회 관찰에서는 `ToolSearch` 줄 없이 이름으로 바로 불렀다. 이름으로 부른 지연 도구를 Claude Code가 어떻게 처리하는지는 확인하지 않았다. 노트북의 Deep Agent는 Skill을 `read_file`로 읽어야 정의를 공개했다(`include_tools`, 01 노트북 3.3절).
3. 서버다. 녹화본의 `event-00000003.json`에서 `gate.source`가 `elicited`이고 대화 상자의 문장도 서버 코드에 있다(`cap_lab/server/server.py:242-246`). 입력이 완료 기준 **문장**이라 닫힌 집합이 아니고, 결과는 세 단계 점수로 줄일 수 있다. 그래서 판단 모델에 두고 통과 여부는 코드(`>=`)가 정한다.
4. "확정해도 되는가"의 입력은 필수 항목 이름 목록이라 닫힌 집합이다. 다만 "내용이 충분한가"는 이 규칙이 보지 않는다(`skills/requirements-interview/SKILL.md:30`). 그 빈자리를 판단 모델이 맡는다.
5. 같은 조건으로 여러 번 돌려 결과가 흔들리는 폭(잡음 폭)을 재고, 바꾼 쪽과 비교해야 한다. 노트북 07의 A·A2·B 비교가 그 방법이다. 사례도 하나가 아니라 여러 개여야 한다.

보태기(4.1절): 아직 판단 모델에 맡길 준비가 되지 않았다. 문턱값 0.5는 재지 않은 자리값이다. 라벨로 재기 전까지는 "모호하면 사용자에게 직접 묻는다"는 안전한 쪽 동작에 기대고 있다.
