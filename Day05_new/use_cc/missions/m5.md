# M5. 평가기를 바꾸는 일도 운영의 일부다 (Part 5 · 평가와 모니터링의 결합 · 50분)

> **핵심 질문: 운영에서 본 실패를 어떻게 사람의 판단, 평가기 변경, 회귀 Golden, 승인 게이트로 이어 붙이나?**
>
> 강의는 `concepts/m5.md` 1~6절(운영 루프, 두 버전 채점, 표본 선정과 annotation queue, 회귀 Golden 승격, 평가기 변경 관리와 backtest, 승인 게이트)을 설명합니다.
> 이 미션은 m3b·m4의 '이어서 처리' 사건을 끝까지 따라갑니다: **사람이 판정하고 → 새 평가기(v2)를 과거 trace에 먼저 돌려 보고 → 회귀 Golden 초안을 만들고 → 채택 여부를 정한다.**

## 이 미션의 비용

| 무엇 | 규모 | 누구의 비용 |
|---|---|---|
| 이 Claude Code 세션 | 약 15~30회(리허설 전 추정) | 내 Claude Code 계정 |
| 에이전트 모델 | 0회(지난 기록을 다시 채점한다) | — |
| Jev, Judge | 0회(궤적 평가기만) | — |
| Langfuse | 사람 검수 큐 1개, 점수 | 내 Langfuse 프로젝트 |
| 배경 운영 로그 검수 큐 (M5-6) | 모델 호출 0회. Langfuse 큐 항목 약 8개와 `human_verdict` 점수 약 2개(읽기만 하고 적재는 m0에서 끝났다) | 내 Langfuse 프로젝트 |

## M5-1. `[따라하기]` 사람 검수 큐에 넣는다 (6분)

> `cc_ops`의 version `agent-v1` 기록에서 `concepts/m5.md` 3절처럼 signal 전략으로 치명 위반 Episode를 고르고, `online.enqueue_for_review(client, "cc-ops-review", selections)`로 Langfuse annotation queue에 넣어 줘. 넣은 수와 건너뛴 수를 보여 줘. `work/m5_queue.py`로.

큐에는 점수 설정 `human_verdict`(PASS/FAIL)가 붙습니다. Langfuse는 점수 설정이 없는 큐를 받지 않습니다(저자 1회 실행에서 400 거절을 보고 `eval_lab`을 고쳤다).

## M5-2. `[내 것 만들기]` 내가 판정한다 (8분)

Langfuse 왼쪽 메뉴 **Human annotation** → `cc-ops-review` → **Process queue**.
trace마다 Tree와 root Output을 읽고, 정책 문서(`data/order_policy.md`)를 기준으로 **이 처리가 맞는지** `human_verdict`를 PASS 또는 FAIL로 고르고 comment에 근거 한 문장을 적습니다. 이 판정은 내 것입니다. Claude Code에게 맡기지 않습니다.

**관찰할 것.** '이어서 처리' trace에 내가 준 판정과 궤적 규칙 v1의 판정(FAIL)이 같은가요? 큐 화면의 Completed/Pending 수.

## M5-3. `[따라하기]` 새 평가기(v2)를 과거 trace에 먼저 돌려 본다: backtest (12분)

m3b에서 만든 `work/m3b_rule_v2.py`를 씁니다.

> `work/m3b_rule_v2.py`의 규칙을 쓰는 평가기 함수를 만들어(입력 계약은 `online.online_evaluators`의 평가기와 같다: `input, output, expected_output, metadata`를 받아 `Evaluation` 목록), 점수 이름 `trajectory_status_v2`로 `cc_ops` version `agent-v1`의 root observation 전체에 `batch_evaluate`로 붙여 줘. 먼저 `wait_for_observations`로 기다려. 그리고 v1(`trajectory_status`)과 v2가 **뒤집힌** observation 수와 목록, Langfuse 주소를 보여 줘. 평가기 코드는 `work/`에만 두고 `eval_lab`은 고치지 마. `work/m5_backtest.py`로.

**먼저 예측하세요.** 20건 중 몇 건의 판정이 뒤집힐까요? 뒤집히는 것은 모두 '이어서 처리'일까요?

**관찰할 것 (Langfuse).** **Scores** 화면에서 같은 Observation에 `trajectory_status`와 `trajectory_status_v2`가 나란히 붙은 줄. 뒤집힌 trace를 열어 M5-2의 내 `human_verdict`와 비교합니다. 사람과 v1, 사람과 v2 중 어느 쪽이 더 자주 같나요? 이 비교는 20건 안의 1회 관찰입니다.

## M5-4. `[따라하기]` 회귀 Golden 초안 (8분)

`evidence.promote_failure`(`concepts/m5.md` 4절의 `promote_failure` 승격 예시)는 **원래 Scenario 카드가 있는 실패**를 승격합니다. '이어서 처리'는 운영에서 처음 본 요청이라 원래 카드가 없습니다. 그래서 같은 세 규칙을 지켜 초안을 만듭니다.

먼저 **내가** 비식별화 확인 기록을 한 문장으로 `notes/m5.md`에 씁니다(이 데이터에 보관하면 안 되는 정보가 없는지 내가 확인했다는 기록. 교육용 가상 데이터라도 내가 씁니다). 그다음 Claude Code에게 부탁합니다.

> '이어서 처리' trace 하나로 회귀 Golden 초안을 `work/m5_regression_draft.json`에 만들어 줘. `promote_failure`와 같은 세 규칙을 지켜: (1) 새 `scenario_id`(`regression-...`)와 출처 trace ID를 `metadata`에, (2) `review_status`는 `pending`, `reviewer`와 `review_reason`은 비워 두고, (3) `expected_output.final_state`는 **비워 둬**(실제 결과를 복사하지 마). `sanitization_record`에는 `notes/m5.md`의 내 문장을 그대로 넣고, 초기 상태는 `fx-ops-resume`을 가리켜. 그다음 이 초안을 `eval_lab.contracts`의 Scenario로 읽어 보면 어떻게 되는지도 보여 줘.

**관찰할 것.** 초안을 Scenario로 읽으려 할 때 어디서 막히는지(`expected_output.final_state`가 비어 있으면 계약이 거부한다, `concepts/m5.md` 4절의 빈 기대 상태 거부 예시). 기대 상태를 비워 두는 이유: 실패한 기록의 상태를 정답으로 적으면 **틀린 행동이 정답으로 굳는다.** 이 초안을 확정하는 것은 담당자의 검수이고, 확정된 카드는 **새 데이터 버전**이 되어 이전 결과와 바로 섞어 비교하지 않습니다.

## M5-5. `[내 것 만들기]` 승인 게이트: v2를 운영 평가기로 쓸 것인가 (6분)

`notes/m5.md`에 결정과 근거를 적습니다. 근거로 쓸 수 있는 것: m3b의 평가기 평가(재현율·오탐률·구간, 주입기가 재지 못한 구멍), M5-3의 backtest(뒤집힌 수), M5-2의 사람 판정과의 일치, M5-4의 회귀 초안. **결정은 내가** 합니다(채택 / 보류 / 더 필요한 증거). Claude Code에게 결정을 묻지 않고, 각 근거가 어느 출력에 있는지만 같이 찾습니다.

## M5-6. `[바꿔보기]` 배경 운영 로그에서 검수 큐 채우기 (5분)

m0에서 `synth_ops`에 적재한 합성 7일 배경 로그를 씁니다(`concepts/m5.md` 7절). 이 단계는 로그를 **읽기만** 하고 다시 적재하지 않습니다. 로컬 기록은 `outputs/notebook/synth-ops/<실행>/episodes.jsonl`입니다.

**먼저 예측하세요.** `signal` 전략으로 뽑은 약 8건은 7일 중 어느 날에서 나올까요? 하루에 몰릴까요, 고르게 퍼질까요?

> `outputs/notebook/synth-ops/` 아래 가장 최근 `episodes.jsonl`을 `eval_lab.synth.read_local_records`로 읽고, `online.select_traces(records, "signal", 8, seed=3)`로 약 8건을 골라 줘. 뽑힌 이유와 `story_day`별 개수를 보여 주고, `online.enqueue_for_review(client, "synth-ops-review", selections)`로 `cc-ops-review`와 **별도의** annotation queue `synth-ops-review`에 넣어 줘. 넣은 수(`enqueued`)와 건너뛴 수(`skipped`)를 출력해. 모델은 부르지 마. `work/m5_synth_queue.py`로.

**관찰할 것 (Langfuse).** 왼쪽 메뉴 **Human annotation** → `synth-ops-review`. 두 건만 열어 Tree와 root Output을 읽고 `human_verdict`를 직접 고릅니다. 그리고 내 판정을 같은 trace의 Code 궤적 평가기 판정(`trajectory_status`)과 비교합니다. 같은가요, 다른가요? 다르다면 평가기와 내 판단 중 무엇이 근거 없이 움직였는지 적어 둡니다. 뽑힌 날짜 분포가 예측과 같았는지도 확인합니다.

이 판정은 합성 trace에 대한 것이라 **모델의 성능이 아니라 평가기를 읽는 내 판단**을 연습합니다.
