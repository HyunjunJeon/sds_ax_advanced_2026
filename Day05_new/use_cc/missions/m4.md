## M4-1. 먼저 예측하세요 (경보 기준을 결과보다 먼저 읽는다, 4분)

`eval_lab/monitoring.py`의 `ALERT_RULES`를 읽습니다(고정 부품이라 고칠 수 없습니다). 기준은 결과를 보기 **전에** 정해 둔 상수입니다.

| 규칙 | 기준 |
|---|---|
| `fatal-rate` | 치명 위반률 > 0 |
| `evaluation-completeness` | 평가 완료율(PASS+FAIL / 전체) < 90% |
| `latency-p95` | p95 지연 > 1일차 p95의 1.5배 |
| `input-mix-shift` | 입력 분포(사건 유형·문형)의 전체 변동 거리 > 0.3 |

`notes/m4.md`에 적습니다. 2일차는 '이어서 처리' 요청이 1일차(10%)보다 많습니다(40%, `ops.py`의 `RESUME_PERCENT`).

1. 1일차와 2일차에 각각 어느 경보가 울릴까요?
2. `fatal-rate`가 울린다면, 그것은 **에이전트가 나빠졌다**는 뜻일까요?

## M4-4. `[따라하기]` 같은 지표를 Langfuse에서 (10분)

> 궤적 평가기만(`online.online_evaluators(...)`의 첫 번째) `batch_evaluate`로 `cc_ops`의 version `agent-v1` root observation에 점수를 붙이고(먼저 `wait_for_observations`로 집계를 기다려), `reference/04-...` 4절처럼 Metrics API v2로 날짜 구간별 root observation 수와 p95 지연을 물어 로컬 값과 나란히 보여 줘. `work/m4_remote.py`로.

**관찰할 것 (Langfuse).**

- 출력의 원격 값과 로컬 값의 차이(`difference`). 기록 직후라면 원격이 적거나 0일 수 있습니다. 1~2분 뒤 다시 실행해 값이 따라오는지 봅니다. 0을 "트래픽이 없다"로 읽지 않습니다.
- **Dashboards → Langfuse Agent Dashboard**(environment `cc_ops`): 도구 호출 수, 많이 불린 도구, 도구 오류, 지연. 2일차에 `release_stock`·`complete_cancellation`이 늘었는지.
- **Scores**: `name:trajectory_status`로 거르고 `cc_ops`의 FAIL이 어떤 trace인지. 그 trace를 열면 m3b에서 본 '이어서 처리'인지.
- (선택, 만들지 않음) **Alerts**: Langfuse의 경보는 Slack·Webhook 같은 목적지를 먼저 연결해야 만들 수 있습니다. 우리 `ALERT_RULES`의 네 규칙 중 무엇을 Langfuse 경보로 옮길 수 있고 무엇은 못 옮기는지(예: 입력 분포 변화) 생각만 해 봅니다.
