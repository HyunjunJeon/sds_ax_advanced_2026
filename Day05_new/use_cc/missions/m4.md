## M4-1. 먼저 예측하세요 (경보 기준을 결과보다 먼저 읽는다, 4분)

| 규칙 | 기준 |
|---|---|
| `fatal-rate` | 치명 위반률 > 0 |
| `evaluation-completeness` | 평가 완료율(PASS+FAIL / 전체) < 90% |
| `latency-p95` | p95 지연 > 1일차 p95의 1.5배 |
| `input-mix-shift` | 입력 분포(사건 유형·문형)의 전체 변동 거리 > 0.3 |

`notes/m4.md`에 적습니다. 2일차는 '이어서 처리' 요청이 1일차(10%)보다 많습니다(40%, `ops.py`의 `RESUME_PERCENT`).

## M4-4. `[따라하기]` 같은 지표를 Langfuse에서 (10분)

> 궤적 평가기만(`online.online_evaluators(...)`의 첫 번째) `batch_evaluate`로 `cc_ops`의 version `agent-v1` root observation에 점수를 붙이고(먼저 `wait_for_observations`로 집계를 기다려), `concepts/m4.md` 4절처럼 Metrics API v2로 날짜 구간별 root observation 수와 p95 지연을 물어 로컬 값과 나란히 보여 줘. `work/m4_remote.py`로.

**관찰할 것 (Langfuse).**

- 출력의 원격 값과 로컬 값의 차이(`difference`). 기록 직후라면 원격이 적거나 0일 수 있습니다. 1~2분 뒤 다시 실행해 값이 따라오는지 봅니다. 0을 "트래픽이 없다"로 읽지 않습니다.
- **Dashboards → Langfuse Agent Dashboard**(environment `cc_ops`): 도구 호출 수, 많이 불린 도구, 도구 오류, 지연. 2일차에 `release_stock`·`complete_cancellation`이 늘었는지.
- **Scores**: `name:trajectory_status`로 거르고 `cc_ops`의 FAIL이 어떤 trace인지. 그 trace를 열면 m3b에서 본 '이어서 처리'인지.
- (선택, 만들지 않음) **Alerts**: Langfuse의 경보는 Slack·Webhook 같은 목적지를 먼저 연결해야 만들 수 있습니다. 우리 `ALERT_RULES`의 네 규칙 중 무엇을 Langfuse 경보로 옮길 수 있고 무엇은 못 옮기는지(예: 입력 분포 변화) 생각만 해 봅니다.

## M4-6. `[따라하기]` 배경 운영 로그 7일 모니터링 (8분)

m0에서 `synth_ops`에 적재한 합성 7일 배경 운영 로그를 **실제 날짜(KST)** 로 모니터링합니다. 이 단계는 읽기만 하고 아무것도 새로 적재하지 않으며 모델을 부르지 않습니다. M4-2의 `cc_ops`(몇 초 만에 끝난 실행을 지금 시각 구간으로 묻는다)와 달리, 이 로그는 날짜를 과거로 당겨 만든 것이라 **날짜마다 하루 구간**으로 묻습니다. 합성 지연·비용은 모델 성능이 아닌 연습용 값입니다(`concepts/m4.md` 7절).

**먼저 예측하세요.** `notes/m4.md`에 적습니다. 7일 중 어느 날짜에 `ALERT_RULES`의 어느 규칙이 울릴까요? 6일차에 `agent-v2`가 일부 섞이면 무엇이 달라질까요(어느 지표, 어느 방향)? 1일차를 기준으로 삼는다는 점을 반영합니다.

> m0의 `synth_load.py`가 남긴 `synth-ops` 폴더의 가장 최근 `episodes.jsonl`을 `eval_lab.synth.read_local_records`로 읽어, `concepts/m4.md` 7절처럼 `monitoring.local_metrics(records, group_by="date")`로 날짜별 지표를 내고 `monitoring.evaluate_alerts`를 날짜마다 첫 날짜를 기준으로 돌려 줘. 그리고 날짜(KST) 하루 구간마다 Metrics API v2(`metrics_query`의 `from_ts`·`to_ts`, 필터는 root observation과 environment `synth_ops`)로 root 개수와 p95 지연을 묻고, version별 개수(로컬은 `records`에서 세고 원격은 `version` 차원으로)도 물어서 원격과 로컬을 나란히 출력해 줘. 지표는 eval_lab 함수 결과를 그대로 쓰고 기준은 읽기만 해. `work/m4_synth.py`로.

**관찰할 것.**

- 날짜별 경보 표. 예측과 어느 날짜·규칙이 맞고 틀렸는지. 경보 기준(`ALERT_RULES`)은 M4-5처럼 고정이며, 합성 로그가 울리게 하거나 안 울리게 하려고 바꾸지 않습니다.
- 원격과 로컬의 `difference`. 이 로그는 지연의 정의가 둘 다 root 길이(`latency_ms`)라 M4-4보다 가까워야 합니다. 그래도 어긋난 날짜가 있으면 집계가 늦은 것인지, 구간(KST 날짜 경계)이 틀린 것인지부터 봅니다.
- **Dashboards**(environment `synth_ops`, 기간 `Past 7 days`): 일별 trace 수 시계열, 지연, 비용, 도구 호출 수. 5일차 오후에 지연이 어떻게 보이는지, 5일차 결제 도구 호출 쪽이 두드러지는지.
- 6일차: `agent-v1`과 `agent-v2`의 개수와, 두 버전의 지표 차이. 7일차: 이어서 처리 요청이 늘어난 입력 분포.
- 지연과 비용(`cost_per_success`)은 합성 값이므로 "모델이 느려졌다"나 "이 모델이 얼마다"로 읽지 않습니다. 이 단계에서 보는 것은 모니터링 **도구가 날짜별로 무엇을 말하는가**입니다.
