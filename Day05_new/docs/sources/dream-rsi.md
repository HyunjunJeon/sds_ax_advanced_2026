## 방법 요약 (자기 말로)

1. **바꾸는 것과 고정하는 것.** 기반 LLM, 코딩 에이전트, 평가기, 실행 인터페이스는 고정한다. 진화하는 대상은 탐색을 조율하는 **정책 코드** 하나다(어느 후보를 펼칠지, 몇 개를 묶어 돌릴지, 언제 멈출지). 모델 가중치는 바뀌지 않는다.
2. **한 라운드 = 세 단계.**
   - 온라인 탐색: 현재 정책으로 실제 탐색을 돌리고, 시도마다 결과(점수, 진단, 상태)를 기록해 탐색 트리를 만든다.
   - 재생 시뮬레이터 만들기: 쌓인 탐색 트리를 다시 쓸 수 있는 시뮬레이터 묶음으로 바꾼다. 재생할 때는 새로 생성하거나 평가기를 다시 돌리지 않고 **기록된 결과를 그대로 꺼내 준다**. 그래서 거의 공짜다.
   - 꿈꾸기(dreaming): LLM 정책 개발 에이전트가 재생 결과와 점수를 보고 정책 코드를 고쳐 후보 여러 개를 만든다. 후보마다 과거 트리 전부에서 재생 점수의 평균을 내고 가장 좋은 것을 다음 온라인 라운드에 내보낸다.
3. **재생 점수.** 찾은 최고 점수에서 시도 비용을 빼고 병렬성에 작은 보너스를 더한 값이다. 식의 계수는 논문에서 정한다.
4. **퇴보 방지.** 현재 정책도 후보에 넣는다. 그래서 과거 기록 기준으로 고른 정책은 현재 정책보다 나쁘지 않다. 다만 이것은 **기록 위에서만** 성립하고, 실제 효과는 다음 온라인 라운드에서 다시 확인한다.
5. **정보 차단.** 재생 중 정책은 이미 관측된 점수만 써야 하고, 아직 공개되지 않은 결과를 엿보면 안 된다(프롬프트로 제약).

## 논문이 밝힌 한계와 이 노트가 덧붙이는 위험

- 재생은 **이미 탐색한 가지 안에서만** 가능하다. 기록에 없는 행동의 결과는 알 수 없다.
- 재생에서는 결과가 고정되지만 실제 생성은 확률적이다. 이 차이가 정책 평가 오차가 된다.
- 과제 8개, 한 모델 계열, 라운드 5~10회로 규모가 작고 반복 분산이나 유의성은 보고하지 않았다.
- 비용을 에이전트 호출 수로만 쟀다.
- (노트 작성자) LLM이 재생 점수를 보고 정책을 고치므로 **재생 점수에 과적합하거나 평가 경로를 건드릴 위험**이 있다. 논문은 이 방어를 자세히 다루지 않는다.

## Day05_new 실습(06)으로 옮길 때의 대응

| Dream-RSI | Day05_new 06 |
|---|---|
| 고정: 기반 LLM, 평가기, 실행 인터페이스 | 고정: `claude-sonnet-5-5` 에이전트와 Prompt, 업무 도구, 평가기(Code → Jev → Judge), 예산 |
| 진화: 탐색 정책 코드 | 진화: **하네스 정책** — 도구 호출이 실행되기 전에 허용·차단·확인 요청을 정하는 결정적 규칙. 개선기는 선언형 정책 명세만 고치고 임의 코드를 실행하지 않는다 |
| 온라인 탐색과 기록 | 모의 운영 트래픽을 실제 모델로 돌리고 Langfuse에 trace와 점수를 남긴다 |
| 탐색 트리 → 재생 시뮬레이터 | 기록된 궤적(도구 호출 순서, 인자, 결과) → 재생 풀. 정책을 각 호출 시점에 적용해 "이 호출을 막았을까"를 계산한다 |
| 꿈꾸기: 후보 정책을 재생 점수로 선택, 현재 정책 포함 | 같다. 점수 식은 PREREG에 미리 고정한다 |
| 다음 온라인 라운드에서 재검증 | holdout 사례를 실제 모델로 다시 실행해 확인한다 |
| (논문에 없음) | 개선기가 평가기, 예산, 테스트를 고치지 못하게 막는다. 루트 `AGENTS.md` 5장의 금지 목록이 그대로 보상 해킹 방지 장치다 |

Prompt를 바꾼 후보는 재생으로 평가할 수 없다. Prompt가 바뀌면 모델의 행동이 갈라져 기록 밖으로 나가기 때문이다. 이것이 06이 하네스 정책을 개선 대상으로 고른 이유다.
