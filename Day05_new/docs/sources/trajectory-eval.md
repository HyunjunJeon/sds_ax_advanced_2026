1. 궤적(trajectory)이란?
2. 왜 점수가 아니라 규칙일까?
3. 순서를 따지는 규칙
4. 7가지 규칙 — 하위 절 "실수해도 바로 고치면 봐준다: 복구 창"

6. 모르면 모른다고 하기

## 아이디어 요약 (자기 말로)

| 아이디어 | 글의 절 | Day05_new에서 쓰는 곳 |
|---|---|---|
| 궤적은 요청부터 마지막 답까지 일어난 사건을 **선후 관계**로 본 기록이다. 걸린 시간보다 순서가 중요하다 | 궤적이란? | 03b 도입 |
| LLM 점수는 같은 기록에도 흔들린다. 규칙 판정은 재현되고 근거를 가리킬 수 있지만, 답의 품질은 보지 못한다. 둘은 잡는 것이 다르다 | 왜 점수가 아니라 규칙일까? | 03b에서 규칙 검사와 DeepEval·Jev·Judge를 나란히 놓는 이유 |
| 규칙은 유한한 기록 위에서 "A가 일어나기 전에 B가 있었는가" 같은 시간 논리 모양을 띤다. 범용 해석기가 아니라 규칙마다 검사 함수를 짠다. 학술 배경은 유한 궤적 위의 선형 시간 논리(LTLf, De Giacomo & Vardi, IJCAI 2013) | 순서를 따지는 규칙 | 03b의 `trajectory_rules` 설계 |
| 규칙을 **치명(fatal)과 경고(warn)** 두 등급으로 나눈다. 치명은 한 번이라도 있으면 실패, 경고는 기록만 한다 | 7가지 규칙 | 03b, 04(위반률 지표를 등급별로) |
| 형식 오류를 낸 뒤 몇 걸음 안에 스스로 고치면 경고로 낮추는 **복구 창**을 둔다 | 복구 창 | 03b 도메인 규칙 하나에 적용 |
| 위험한 행동의 허락은 질문이 아니라 **긍정 응답**이어야 하고, 그 응답이 실행보다 **먼저** 와야 한다. 부정하거나 다른 행동을 허락한 응답은 허락이 아니다 | 위험한 명령은 허락이 먼저 | 03b — 주문 번호 확인 없이 쓰기, 다른 고객 주문 쓰기 |
| 판정은 PASS와 FAIL만이 아니다. 기록이 불완전하면 INCOMPLETE, 진행 중이면 PROVISIONAL, 기록이 없으면 NO_EVIDENCE. 판정 순서는 기록 완전성 → 진행 여부 → 기록 존재 → 치명 위반. 읽기 예산을 넘으면 INCOMPLETE. **PASS는 "관측한 범위에서 위반이 없었다"는 뜻일 뿐 좋은 작업의 인증이 아니다** | 모르면 모른다고 하기 | 03b 판정 상태 5종, 04의 "평가 완료율" |
| 출력에 찍힌 문자열, 도움말, 인용, 질문만 한 것은 실행이나 승인으로 보지 않는다. 해석이 어려우면 보류한다 | 글자는 행동이 아니다 | 03b — 응답에 "환불했습니다"라고 쓴 것과 실제 `refund_payment` 사건을 가른다 |
| 평가기도 평가한다. 결함을 일부러 심은 기록(재현율), 정상인데 모양만 바꾼 기록(오탐률), 실제 위반 검토(정밀도). 비율에는 Wilson 95% 신뢰 구간을 붙인다 | 평가기는 어떻게 평가했을까? | 03b 평가기 평가, 06 개선기의 가드 |
| 숫자가 좋아져도 일부는 측정 정책을 바꾼 효과일 수 있다. 개선과 측정 변경을 섞지 않는다 | 결과: v3에서 v4로 | 05 평가기 변경 관리 |
| 평가기로 기록을 채점 → 실패 패턴 찾기 → 하네스 수정 → 과거 기록을 고친 하네스에 **반사실 재생**. 정상이던 호출이 바뀌지 않았는지도 본다. 재생은 다른 변경의 안전장치(변경 게이트)로도 쓴다. 증거가 모자라면 끝까지 보류한다 | 평가기로 하네스 고치기 | 06 RSI 루프의 "재생" 단계 |
| 한계: 독립 평가가 아니고 표본이 작으며 심지 않은 종류의 실수는 재지 않았다. 답의 유용성이나 코드 정확성은 보지 않는다 | 아직 모르는 것 | 03b·06의 "이 평가가 말해 주지 않는 것" |
