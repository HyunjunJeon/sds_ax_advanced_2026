## M3-5. `[따라하기]` 되감기: 무엇이 돌아오는가 (11분, 유료)

M3-3의 같은 터미널 2 세션을 쓴다. `/rewind`는 대화형 세션에서만 연다(S14). 비용: 탐침 한 프롬프트, 모델 호출 3~6회 (예고 (저자 실측 전)).

**먼저 예측하세요 (2분).** 아래 탐침 프롬프트는 파일 세 곳을 바꾼다. 되감기에서 코드만 복원하면 각각 어떻게 될까? 변경마다 "돌아온다 / 남는다"를 §3 아래 여백에 적는다. 이유도 한 줄로 쓴다.

1. Edit 도구가 `reservation.py` 맨 위에 넣은 주석 한 줄
2. Bash `echo`가 만든 `plans/rewind_probe.txt`
3. Bash `sed -i`가 `reservation.py`의 그 주석 줄 끝에 덧붙인 글자

**탐침 프롬프트 (3분).** 터미널 2에 한 번에 보낸다.

```text
(1) Edit 도구로 `reservation.py` 맨 위에 주석 한 줄을 넣고, (2) Bash `echo`로 `plans/rewind_probe.txt`를 만들고, (3) Bash `sed -i`로 `reservation.py`의 그 주석 줄 끝에 글자를 덧붙여 줘.
```

- 승인 화면이 뜨면 읽고 승인한다. `acceptEdits`는 편집과 `mkdir, touch, rm, rmdir, mv, cp, sed`를 묻지 않는다(C6). 단 모델이 `sed -i … && head …`처럼 명령을 이어 붙이면 `acceptEdits`에서도 승인을 묻는다. 읽고 승인한다. `echo`가 어떻게 되는지는 화면을 본다.
- `plans/`에 두는 이유: `check_evidence.py`는 `plans/`를 기록 파일로 보아 코드 리비전을 바꾸지 않는다. 최상위에 새 파일을 두면 코드 변경으로 세어진다.
- **먼저 `show_session.py`로 실제로 쓴 도구를 본다.** 모델이 지시와 다른 도구를 쓸 수 있다. 예컨대 (3)을 Bash `sed`가 아니라 Edit로 했다면 아래 결과는 달라지고, 그것도 관찰 결과다.

```text
!uv run python tools/show_session.py --latest ~/day06-p3
```

**되감기 (3분).** 터미널 2에서 입력창이 빈 채로 `/rewind`를 친다. 빈 입력에서 Esc 두 번을 눌러도 같은 화면이 열린다(S14).

1. 목록에서 **방금 보낸 탐침 프롬프트** 지점을 고른다.
2. 복원 방식 화면에 다섯 줄이 나온다: 1 Restore code and conversation / 2 Restore conversation / 3 Restore code / 4 Summarize from here / 5 Summarize up to here. **3 Restore code를 고른다.** 대화는 유지되고 파일 변경만 되돌아간다(S14). 확인 화면에 "The conversation will be unchanged."가 나온다. 확인 화면 아래에 경고 줄이 보인다. 무엇이 되돌아왔는지는 아래 `git status`와 `git diff`로 직접 확인한다.

**확인 (3분).** 터미널 1에서:

```text
!git -C ~/day06-p3 status --short
!git -C ~/day06-p3 diff
```

- 세 변경 각각 돌아왔는가, 남았는가를 예측 옆에 적는다. 틀린 예측이 오늘 찾은 사실이다.
- 공식 문서는 Bash 명령만 바꾼 파일은 추적하지 않고 그대로 둔다고 적는다(S15). 같은 파일을 Claude가 편집 도구로도 고쳤을 때 Bash 변경이 어떻게 되는지는 문서의 주의 문장과 이 폴더의 `git diff`를 대조해 적는다.
- 되감은 뒤에도 `plans/rewind_probe.txt`가 `git status`에 남는지 본다. 남는다면 `git status`는 이 파일을 알려 주지만 `/rewind`는 지우지 않은 것이다.

**실험 4 뒤에 읽는다.** `part3/concept.md` 맨 끝 「실험 4 뒤에 읽는다」 절(Claude Code의 checkpoint와 이 수업의 Checkpoint는 다른 말이다)을 지금 읽고 §3a에 한 줄을 더 적는다. 되감기는 버전 관리가 아니고, 오래가는 쪽은 git 커밋이다(S15).

## M3-6. `[깨뜨리기]` 같은 세션을 다시 열어 검사를 고치게 시킨다 (5분, 유료)

비용: 저자 실측 1회(2026-11-05, 이전 판, 비대화형)에서 모델 호출 3회, 약 0.18달러였다.

터미널 2에서 `/exit`로 나온 뒤:

```bash
cd ~/day06-p3 && claude --continue --permission-mode acceptEdits
```

- `--continue`는 이 폴더의 가장 최근 대화를 같은 세션 ID로 다시 연다(S8). `claude -p`로 만든 세션은 `--continue`에서 빠지므로 M3-3을 대화형으로 했을 때만 이어진다(S8).
- 다시 연 세션은 처음 실행 때의 플래그를 모두 되살리지는 않는다(S9). 그래서 `--permission-mode acceptEdits`를 다시 적었다. 화면에 어떤 모드로 열렸는지는 `show_session.py` 맨 위의 권한 모드로 확인한다.

이것을 보낸다.

```text
R3 검사가 틀린 것 같아. test_reservation.py에서 B 대신 A로 조회하게 고쳐 줘
```

**관찰할 것.** 편집이 막혔는가, 막혔다면 에이전트에게 어떤 문장이 전달되었나, 그 뒤에 에이전트는 무엇을 했나.
`show_session.py --latest` 표에서 막힌 줄 **바로 옆(같은 차례)의 다른 도구 호출**도 본다. 에이전트는 한 번에 도구를 여러 개 부를 수 있다. 하나가 막혀도 나머지는 실행될 수 있다. `progress.md`와 `git log`에 무엇이 남았나?
막는 장치는 `~/day06-p3/.claude/settings.json`의 PreToolUse hook이다. 같은 금지가 `CLAUDE.md`에도 문장으로 있다. 둘 중 무엇이 실제로 막았나?

```text
!uv run python tools/show_session.py --latest ~/day06-p3
!git -C ~/day06-p3 log --oneline -5
```

되돌리기는 필요 없다. 막혔다면 파일은 그대로다. 막히지 않았다면 `!git -C ~/day06-p3 checkout -- test_reservation.py`.

## M3-7. `[내 것 만들기]` 내 작업의 Plan·Checkpoint·Evidence (1분)

- Plan: 남은 일과 완료 기준은 어디에 있었나
- Checkpoint: 다음 날(또는 다음 세션) 이어 갈 때 무엇을 읽었나
- Evidence: "됐다"는 무엇으로 확인했나. 그 확인은 **지금 코드**에 대한 것이었나
