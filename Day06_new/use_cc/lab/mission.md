# 실습. 개인 AI SDLC 설계 (55분)

> **핵심 질문: 내 AI 활용에서 반복되는 문제는 무엇이고, 어느 책임을 어떤 장치로 채우면, 무엇으로 나아졌다고 말할 수 있는가?**
>
> 네 단계로 한다: 진단(15분) → 분류(10분) → 설계(20분) → 지표(10분).
> 이 실습이 끝나면 `notes/MY_AI_SDLC.md`의 §6~§9가 채워지고, 오늘의 파일 하나가 완성된다.

## 이 실습의 비용

| 무엇 | 규모 | 누구의 비용 |
|---|---|---|
| 터미널 1의 조교 세션 | Claude Code 호출 약 10~25회(예고. 저자 실측 전). 3단계에서 장치 초안을 쓰면 늘어난다 | 내 Claude Code 계정 |
| 선택: `/insights` | 최근 세션을 분석해 보고서를 만들고 내 요금제·API 토큰을 쓴다(공식 문서). 규모는 문서에 없고 저자 확인 전이다 | 내 Claude Code 계정 |

`diagnose_sessions.py`, `harness_inventory.py`는 모델을 부르지 않는다.

## 먼저: 업무 세션을 다루는 규칙 (반드시 읽는다)

이 실습은 **내 업무 세션 기록**을 다룬다. 세션 기록에는 대화, 도구 호출, 도구 결과가 그대로 들어 있다.

1. 조교 세션(Claude Code 안)에서는 **기본 출력만** 실행한다. 기본 출력에는 건수와 번호만 나온다.
2. 내용을 보는 `--show`와 이름을 보는 `--reveal`은 **Claude Code 밖의 일반 터미널**에서만 친다. Claude Code 안에서 `!`로 치면 출력이 대화에 들어가 모델로 전송된다. 도구도 거절한다.
3. 업무 코드·고객 정보·대화 원문을 조교에게 붙여 넣지 않는다. **내 말로 한두 문장 요약**한다.
4. **회사 정책이 우선이다.** 정책상 세션 기록을 분석할 수 없으면 Part 3·5의 실험 폴더 세션으로 같은 실습을 한다(`--project ~/day06-p3`).

## 1단계. 진단 (15분)

`[따라하기]` 조교 세션에서:

```text
!uv run python tools/diagnose_sessions.py --days 14
```

- 세션이 0개면 `--days 30`으로 늘린다. 그래도 없으면 실험 폴더로 한다: `--project ~/day06-p3`.
- 이 도구는 Claude Code 기록만 읽는다. 다른 도구(Codex, GJC 등)의 세션은 세지 않는다.

**관찰할 것.**
- 건수가 가장 큰 신호와, 세션 수가 가장 큰 신호(여러 세션에 퍼진 문제)
- "많이 쓴 도구" 줄
- 신호는 휴리스틱이다. "다시 볼 곳"이지 판정이 아니다

§6 표에 옮겨 적는다.

## 2단계. 분류 (10분)

1단계 표의 "위치 예"에서 **다시 볼 곳 세 개**를 고른다(예: `P3:28dd395f#7`).

`[따라하기]` **일반 터미널**(Claude Code가 아닌 새 셸)에서:

```bash
cd Day06_new/use_cc
uv run python tools/diagnose_sessions.py --show P3:28dd395f#7
```

- 그 차례의 사람 발화, 도구 호출, 결과 앞부분이 나온다. **이 화면은 나만 본다.**
- 위치마다 §7 표에 **내 말로** 적는다: 실제로 무슨 일이었나, 실패한 책임, SDLC 단계, 이런 일을 몇 번 봤나.

책임을 고르기 어려우면 이 질문으로 좁힌다(정답표가 아니라 질문이다).

| 신호 | 물어볼 질문 |
|---|---|
| 같은 명령 반복, 실패 뒤 같은 재시도 | 결과를 보고 다음 행동을 바꾸게 하는 장치가 있었나? (실행 제어·도구) |
| 도구 사용 거절 | 무엇을 해도 되는지 미리 알려 주었나? 내가 거절한 기준은 어디에 적혀 있나? (지침·실행 제어) |
| hook이 막음 | 막힌 뒤 에이전트는 무엇을 했나? 같은 차례의 다른 도구 호출은 실행되었나? 이 숫자는 내 장치가 실제로 일한 증거이기도 하다 (실행 제어·기록) |
| 사람이 중단 | 에이전트가 무엇을 하려는지 내가 예상할 수 있었나? 완료 조건을 주었나? (지침) |
| 수정 뒤 검사 없음 | 무엇을 실행하면 확인되는지 에이전트가 알았나? (검증) |
| 검사 파일 수정 | 새 검사를 쓴 것인가, 실패하는 검사를 고친 것인가? (검증, 신뢰 기반) |
| 문맥 압축 | 압축 뒤에 이어 갈 사실이 파일로 있었나? (상태) |

## 3단계. 설계 (20분)

§7의 문제마다 **장치 종류 하나**를 고른다. 이 질문들로 고른다.

| 질문 | "예"면 |
|---|---|
| 에이전트가 **몰라서** 생긴 문제인가? 알려 주면 되나? | Rule(CLAUDE.md 한 줄). 절차가 길면 Skill |
| 알려 줬는데도 반복되나? **한 번이라도** 일어나면 안 되나? | Hook(실행 제어). 플레이북: "The skill makes violations rare and the hook makes them close to impossible." |
| 에이전트가 **볼 수 없는** 정보·환경 때문인가? | Tool(CLI, MCP) |
| "됐다"를 **확인할 방법**이 없나? | Evaluation(검사, 평가 사례) |

참고(플레이북 원문, 저자 번역):
- "When Claude makes a mistake twice, the correction goes into CLAUDE.md." — 같은 실수를 두 번 하면 그 교정을 CLAUDE.md에 넣는다.
- 평가 사례는 최근 실제 작업 20~50개로 만들라고 권한다("collects 20 to 50 real tasks from recent work"). 오늘은 **내 세션에서 3개**로 시작한다.

§8 표를 채운 뒤, **하나를 실제로 만든다.**

- 코드와 문장 초안은 조교(Claude)가 써도 된다. **무엇을 만들지, 왜 그 종류인지, 언제 쓰지 않는지는 내가 정한다.**
- 만드는 곳은 이 저장소 밖이다: 내 업무 폴더(회사 정책을 확인한다) 또는 실험 폴더(`~/day06-p3`).
- 만든 뒤 **그것이 동작하는지 한 번 확인한다.** Hook이면 일부러 막힐 행동을 시켜 본다(실험 폴더에서). Rule이면 다음 세션에서 그 규칙이 실렸는지 `/memory`로 본다. Evaluation이면 한 번 실행한다.

## 4단계. 지표 (10분)

§9에 지표 2~3개를 적는다. 플레이북의 측정 지표를 개인 단위로 옮긴 예(원문은 영어, 번역은 저자):

| 플레이북 지표(원문) | 내 단위로 옮기면 |
|---|---|
| "How often Claude repeats a mistake CLAUDE.md should have caught." (선행) | 같은 교정을 다시 해야 했던 횟수 |
| "First-pass CI success rate for agent-written changes" (선행) | 에이전트가 바꾼 뒤 첫 검사가 통과한 비율 |
| "Rework cycles per change … and how often the merged diff still matches the committed plan.md." (후행) | 작업 하나당 다시 고친 횟수, 계획과 결과가 맞았는지 |
| "Time from first conversation to a committed intent.md" (선행) | 첫 대화에서 의도 문서가 생기기까지 걸린 시간 |

- **선행 지표**는 바뀐 행동을 빨리 보여 준다. **후행 지표**는 결과를 늦게 보여 준다. 하나씩은 고른다.
- **기준선**은 지금 값이다. 1단계 진단 결과에서 가져와도 된다(예: "수정 뒤 검사 없음" 건수 ÷ 사람 차례 수).
- **다시 잴 때와 같은 조건**을 적는다: 같은 기간 길이, 같은 도구, 비슷한 작업.
- 오늘 만든 장치가 오늘 한 번 동작한 것은 개선의 증거가 아니다. better-harness README의 문장이 이것을 정확히 말한다.

  > "Passing a current check proves that the intervention was exercised; only a comparable later result can prove that the loop improved."

- 마지막 줄 "이 지표로 말할 수 없는 것"을 꼭 쓴다. 예: 검사 명령을 많이 치게 하면 지표는 좋아지지만 검사가 의미 있는지는 말해 주지 않는다.
