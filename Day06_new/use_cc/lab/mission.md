# 실습. 개인 AI SDLC 설계 (개념 5분 + 미션 55분 + 마무리 5분)

> **핵심 질문: 내 반복 실패를 어느 장치로 막고, 좋아졌다는 것을 무엇으로 재는가?**
>
> 네 단계로 한다: 진단(12분) → 분류(10분) → 설계·만들기·확인(23분) → 지표(10분). 합이 55분이다.
> 네 단계는 실습 제목의 네 항목에 대응한다. 진단 = 채팅형 Agent 활용 방식 진단, 분류 = 반복 작업·품질 문제 식별, 설계·만들기·확인 = 필요한 Rules·Skills·Tools·Evaluation, 지표 = 개발 성과 개인 지표.
> 이 실습이 끝나면 `notes/MY_AI_SDLC.md`의 §6~§9가 채워지고, 장치 하나가 실제로 만들어져 동작이 확인된다.

터미널은 둘이다. **터미널 1**은 `Day06_new/use_cc`의 조교 세션이고 셸 명령 앞에 `!`를 붙인다. **터미널 2**는 실험 폴더에서 여는 실험 대상 세션이다(`cd ~/day06-lab && claude --permission-mode acceptEdits`).

## 이 실습의 비용

| 무엇 | 규모 | 누구의 비용 |
|---|---|---|
| 터미널 1의 조교 세션 | 차례 약 10~25회. 3단계에서 장치 초안을 쓰면 늘어난다 (예고, 저자 실측 전) | 내 Claude Code 계정 |
| 3단계 실험 11, 터미널 2의 실험 대상 세션 | PostToolUse 시작 틀: 모델 호출 8회, 약 0.13달러. SessionStart 시작 틀: 호출 1회, 약 0.03달러. 합 9회, 약 0.16달러 (저자 실측 1회 (2026-11-06, Sonnet 5.5, 비대화형). 대화형은 다를 수 있다) | 내 Claude Code 계정 |
| 선택: `/insights` | 최근 세션을 모델이 읽어 보고서를 만들고 내 요금제·API 토큰을 쓴다(V11). 규모는 문서에 없다. 쓰기 전에 알리고, 쓰고 싶을 때만 한다 | 내 Claude Code 계정 |
| `diagnose_sessions.py`, `harness_inventory.py`, `show_session.py` | 모델을 부르지 않는다 | 없음 |

## 먼저: 업무 세션을 다루는 규칙 (반드시 읽는다)

이 실습은 **내 업무 세션 기록**을 다룬다. 세션 기록에는 대화, 도구 호출, 도구 결과가 그대로 들어 있다.

1. 조교 세션(Claude Code 안)에서는 **기본 출력만** 실행한다. 기본 출력에는 건수와 번호만 나온다.
2. 내용을 보는 `--show`와 이름을 보는 `--reveal`, `harness_inventory.py --json`은 **Claude Code 밖의 일반 터미널**에서만 친다. Claude Code 안에서 `!`로 치면 출력이 대화에 들어가 모델로 전송된다. 도구도 거절한다.
3. 업무 코드·고객 정보·대화 원문을 조교에게 붙여 넣지 않는다. **내 말로 한두 문장 요약**한다.
4. **회사 정책이 우선이다.** 정책상 세션 기록을 분석할 수 없으면 Part 3·5의 실험 폴더 세션으로 같은 실습을 한다(`--project ~/day06-p3`).

## 개념 (5분): 장치 고르기 표

내 반복 실패를 막는 장치는 여럿이다. 아래 표로 "언제 이 장치인가"를 고른다. 근거 번호는 `docs/sources/claude_code/`의 대장 항목이다.

| 장치 | 언제 | 근거 |
|---|---|---|
| Rule(개인): `~/.claude/CLAUDE.md`, `CLAUDE.local.md` | 나만의 습관·선호, 이 컴퓨터에서만. 강제 아님 | I1, I15, I8 |
| Rule(팀): 프로젝트 `CLAUDE.md`, `.claude/rules/` | 항상 필요한 맥락, 두 번 고친 것, 저장소로 팀과 공유. 강제 아님 | I1, I15, I6, I5, I8 |
| Skill | 가끔 필요한 지식·절차. 부작용이 있으면 `disable-model-invocation` | I15, I11, I12, I16 |
| Hook | 매번 같은 방식으로 일어나야 하는 것 | I15, C13, C15 |
| Hook 시작 틀 ① PostToolUse | 편집 뒤 검사를 자동으로 돌린다. 시작 틀 하나를 복사해 검사 명령만 바꾼다. exit 2는 Claude에게 이유를 돌려준다 | C21, C13 |
| Hook 시작 틀 ② SessionStart | 세션이 시작될 때 진행 상황(`progress.md` 요약)을 맥락으로 출력한다. 시작 틀을 복사해 내 파일로 바꾼다 | C20, C13 |
| 권한 규칙 | 묻거나 막을 도구 호출 | C1, C2, C4 |
| 하위 에이전트 | 맥락 격리, 새 눈의 검토 | I15, X2, X3 |
| Tool(MCP, CLI, plugin `bin/`) | 바깥 시스템 연결 | I15, T8, T10, T20 |
| Evaluation | 통과/실패 검사, Stop hook, plugin 효과는 Δ(plugin 유무 차이)로 | I17, C16, V3 |
| 지표 | Claude Code가 내보내는 숫자: `/usage`, OpenTelemetry 지표(세션·비용·토큰·편집 결정 등), 본문은 기본 제외 | V10, V7, V9 |
| 진단 보조(선택) | `/insights`: 최근 세션을 모델이 읽고 토큰을 쓴다 | V11 |

- 분석 대시보드는 관리자만 보므로 개인 지표에 쓰지 않는다(V13).
- `claude plugin eval`은 Δ의 생각만 빌리고 오늘 실행하지 않는다. 실행마다 실제 모델 호출이 든다(V5).
- 장치를 만든 뒤에는 "실렸나"와 "쓰였나"를 따로 확인한다(V12).

## 1단계. 진단 (12분) → §6

`[따라하기]` 조교 세션에서 (업무 폴더 대신 실험 폴더로 하려면 `--project ~/day06-p3`를 붙인다):

```text
!uv run python setup_sandbox.py ~/day06-lab
!uv run python tools/diagnose_sessions.py --days 14
!uv run python tools/harness_inventory.py <내 업무 폴더 또는 ~/day06-lab>
```

- 첫 줄은 실험 폴더 `~/day06-lab`을 만든다(기본 폴더를 쓸 때). 업무 폴더만 볼 거면 건너뛰어도 된다. 이미 만들었으면 건너뛴다. 다시 치면 `[거절]`이 나오고 폴더는 그대로다.

- 세션이 0개면 `--days 30`으로 늘린다. 그래도 없으면 실험 폴더로 한다: `--project ~/day06-p3`.
- `diagnose_sessions.py`의 기본 출력은 하위 에이전트 기록 수도 센다(파일 개수만, 내용 없음). 이 도구는 Claude Code 기록만 읽는다. 다른 도구의 세션은 세지 않는다.
- `harness_inventory.py`는 그 폴더에서 Claude Code에 실리는 것을 여섯 책임으로 센다(개수만). 지금 숫자는 장치를 만들기 전 "실린 것"의 기준선이다. §6에 적어 두면 3단계에서 비교한다.

**관찰할 것.**
- 건수가 가장 큰 신호와, 세션 수가 가장 큰 신호(여러 세션에 퍼진 문제)
- "많이 쓴 도구" 줄
- 신호는 휴리스틱이다. "다시 볼 곳"이지 판정이 아니다

§6 표에 옮겨 적는다.

### 선택: `/insights`

이 기계의 최근 세션을 모델이 읽고 보고서를 만든다(V11). **토큰을 쓰므로** 하고 싶을 때만 한다. 보고서 내용을 조교에게 붙여 넣지 않는다. 안 해도 이 실습은 끝난다.

## 2단계. 분류 (10분) → §7

1단계 출력의 "위치 예"에서 **다시 볼 곳 세 개**를 고른다(예: `P3:28dd395f#7`).

`[따라하기]` **일반 터미널**(Claude Code가 아닌 새 셸)에서:

```bash
cd Day06_new/use_cc
uv run python tools/diagnose_sessions.py --show P3:28dd395f#7
```

- 그 차례의 사람 발화, 도구 호출, 결과 앞부분이 나온다. **이 화면은 나만 본다.** 차례 내용은 조교 세션에 붙여 넣지 않는다.
- 위치마다 §7 표에 **내 말로** 적는다: 실제로 무슨 일이었나, 실패한 책임(여섯 책임 중 하나), SDLC 단계, 이런 일을 몇 번 봤나.

책임을 고르기 어려우면 이 질문으로 좁힌다(정답표가 아니라 질문이다).

| 신호 | 물어볼 질문 |
|---|---|
| 같은 명령 반복, 실패 뒤 같은 재시도 | 결과를 보고 다음 행동을 바꾸게 하는 장치가 있었나? (실행 제어·도구) |
| 도구 사용 거절 | 무엇을 해도 되는지 미리 알려 주었나? 내가 거절한 기준은 어디에 적혀 있나? (지침·실행 제어) |
| hook이 막음 | 막힌 뒤 에이전트는 무엇을 했나? 같은 차례의 다른 도구 호출은 실행되었나? 이 숫자는 내 장치가 실제로 일한 증거이기도 하다 (실행 제어·기록) |
| 사람이 중단 | 에이전트가 무엇을 하려는지 내가 예상할 수 있었나? 완료 조건을 주었나? (지침) |
| 수정 뒤 검사 없음 | 무엇을 실행하면 확인되는지 에이전트가 알았나? (검증) |
| 검사 파일 수정 | 새 검사를 쓴 것인가, 실패하는 검사를 고친 것인가? (검증) |
| 문맥 압축 | 압축 뒤에 이어 갈 사실이 파일로 있었나? (상태) |

## 3단계. 설계·만들기·확인 (23분) → §8

**먼저 예측하세요.** 장치를 고르기 전에 `notes/MY_AI_SDLC.md` §8의 두 줄에 적는다.

- `예측 (실렸나)`: 이 장치가 **실렸다**는 것을 무엇으로 확인할 것인가?
- `예측 (쓰였나)`: 이 장치가 **쓰였다**는 것을 무엇으로 확인할 것인가?

### 3-1. 고른다 (5분)

§7의 문제마다 위 장치 표에서 **장치 하나**를 고른다. 이 질문으로 좁힌다.

| 질문 | "예"면 |
|---|---|
| 에이전트가 **몰라서** 생긴 문제인가? 알려 주면 되나? | Rule. 절차가 길면 Skill |
| 알려 줬는데도 반복되나? **한 번이라도** 일어나면 안 되나? | Hook 또는 권한 규칙 |
| 에이전트가 **볼 수 없는** 정보·환경 때문인가? | Tool(CLI, MCP) |
| "됐다"를 **확인할 방법**이 없나? | Evaluation(검사, Stop hook) |

- 코드와 문장 초안은 조교 세션이 써도 된다. **무엇을 만들지, 왜 그 종류인지, 언제 쓰지 않는지는 내가 정한다**(`use_cc/CLAUDE.md` 4장).
- §8 표를 채운다.

### 3-2. 만든다 (10분, 실험 11)

기본은 1단계에서 만든 실험 폴더 `~/day06-lab`에서 한다. 업무 폴더는 선택이고, 회사 정책을 먼저 확인한다. 실험 폴더가 없으면 1단계의 첫 줄을 먼저 실행한다.

**Hook을 고른 경우** 시작 틀 두 개 중 하나에서 출발한다. 위치는 `lab/hook_templates/`다.

| 파일 | 하는 일 | 바꿀 곳 |
|---|---|---|
| `post_tool_use_check.py` | 파일을 고친 직후 검사를 돌리고, 실패하면 exit 2와 출력 끝 20줄을 Claude에게 돌려준다(C21) | 파일 위쪽 `CHECK_COMMAND` 하나 |
| `session_start_progress.py` | 세션이 시작될 때 `progress.md` 앞 40줄과 최근 git 기록 5개를 맥락으로 출력한다(C20) | 읽을 파일 이름 |
| `settings_example.json` | 두 hook을 settings에 거는 예. PostToolUse는 `Edit\|Write\|MultiEdit`에만, SessionStart는 `startup\|resume\|compact`에 건다 | 필요한 쪽만 |

복사는 조교 세션에서 한다.

```text
!mkdir -p ~/day06-lab/.claude/hooks && cp lab/hook_templates/post_tool_use_check.py lab/hook_templates/session_start_progress.py ~/day06-lab/.claude/hooks/
```

실험 폴더에는 이미 `.claude/settings.json`이 있다(권한 규칙과 PreToolUse hook 하나가 들어 있다). **`settings_example.json`으로 덮어쓰지 않는다.** 그 파일의 `PostToolUse` 또는 `SessionStart` 항목을 기존 `hooks` 안에 **덧붙인다.** 덧붙이는 편집은 조교 세션에게 시켜도 된다. 어느 hook을 왜 거는지는 내가 정한다.

기본 `CHECK_COMMAND`는 테스트 전체를 돌린다. 폴더에 이미 실패하는 검사가 있으면(실험 폴더의 R3) 어떤 편집이든 실패로 알려지므로, 내 편집이 깨뜨린 것인지 원래 깨져 있던 것인지 구분되지 않는다. `CHECK_COMMAND`를 지금 작업하는 요구의 검사 하나로 좁혀서 쓴다. 편집 뒤 알림이 오면 어느 검사의 실패 출력인지 읽고, 내 편집 탓인지 원래 깨진 검사 탓인지 구분한다.

한계를 알고 쓴다. PostToolUse는 도구가 이미 성공한 뒤에 돈다. exit 2는 편집을 되돌리지 못하고 Claude에게 이유를 보여 줄 뿐이다(C21). Bash 명령이 파일을 고친 경우는 matcher에 걸리지 않는다(C14). 두 시작 틀은 저자가 비대화형 세션 1회로 동작을 확인했다(2026-11-06). 대화형 화면은 확인하지 않았다. 내 환경에서 동작하는지는 3-3에서 직접 본다.

**Rule·Skill·권한 규칙·하위 에이전트를 고른 경우** 같은 실험 폴더에 만든다. 조교 세션이 초안을 쓰고 내가 읽고 고친다.

### 3-3. 확인한다 (8분)

**실렸나.** 터미널 2에서 실험 대상 세션을 연다.

```text
cd ~/day06-lab && claude --permission-mode acceptEdits
```

폴더 신뢰 화면이 뜨면 읽고 수락한다. 그다음 고른 장치에 맞는 명령을 친다(V12).

| 고른 장치 | 실렸는지 보는 곳 |
|---|---|
| Rule | `/context all`의 Memory files 목록, `/memory` |
| Hook | `/hooks` (읽기 전용 화면. `[Project]` 같은 출처 라벨, 안으로 들어가면 `Source: Project settings (.claude/settings.json)`) |
| Skill | `/skills` (프로젝트 Skill은 `project`로 표시) |
| 권한 규칙 | `/permissions` |
| 전부 | 조교 세션에서 `!uv run python tools/harness_inventory.py ~/day06-lab`의 개수가 1단계 값에서 늘었는지 |

`/hooks` 목록에 설정 항목이 보여도 그 hook 파일이 실제로 있다는 뜻은 아니다(설정이 있다 ≠ 파일이 있다). 목록에 없으면 "쓰이지 않는다"가 아니라 **"실리지 않았다"**부터 의심한다.

**쓰였나.** 실험 대상 세션에서 장치가 일할 요청 하나를 보낸다. 예: 검사가 깨지는 파일 편집을 시킨다(Hook), 규칙이 말한 행동을 하게 한다(Rule). 끝나면 `/exit`로 나와 조교 세션에서 본다.

```text
!uv run python tools/show_session.py --latest ~/day06-lab
```

표에서 장치가 일한 흔적(Skill 호출, 거절된 도구 호출 등)을 찾는다. PostToolUse hook이 알린 내용은 이 표의 도구 결과 칸에 나오지 않고, 기록 파일(jsonl)에 "편집 뒤 검사가 실패했습니다" 줄로 남는다(저자 실측 1회 (2026-11-06)). 그 줄은 기록 파일에서 직접 찾는다. 처음 적은 예측과 비교해 §8의 "쓰였는지 확인한 방법 (세션 기록에서 무엇을 봤나)"에 적는다. "실렸나"의 결과는 "불러와졌는지 확인한 방법"에 적는다. **한 번의 관찰은 "1회 관찰"이다.**

## 4단계. 지표 (10분) → §9

§9에 개인 지표 2~3개를 적는다. 재료는 Claude Code가 내보내는 숫자로 한정한다.

| 재료 | 무엇이 나오나 | 주의 |
|---|---|---|
| `/usage` | 내 사용량(V10) | 어느 화면에 무엇이 보이는지는 직접 열어 확인한다 |
| OpenTelemetry 지표 | 세션·비용·토큰·편집 결정 등(V7) | 본문은 기본 제외다. 본문을 담는 스위치는 켜지 않는다(V9). 지표를 받을 곳(수집기)은 오늘 만들지 않는다 |
| 1단계 진단 도구 | 신호 건수 | 그 도구의 신호는 휴리스틱이다 |

- **선행 지표**는 바뀐 행동을 빨리 보여 주고, **후행 지표**는 결과를 늦게 보여 준다. 하나씩은 고른다.
- **기준선**은 지금 값이다. 1단계 진단 결과에서 가져와도 된다.
- **비교할 때 같아야 할 것**을 적는다: 같은 기간 길이, 같은 종류의 일, 같은 모델, 장치만 다름.
- 오늘 장치가 한 번 동작한 것은 개선의 증거가 아니다. 비슷한 조건의 나중 결과만 개선을 말할 수 있다.
- 마지막 줄 "이 지표로 말할 수 없는 것"을 꼭 쓴다. 예: 검사를 많이 치게 하면 지표는 좋아지지만 검사가 의미 있는지는 말해 주지 않는다.
