# 나의 AI SDLC — 강사 예시

> 강사가 Claude Code(Opus 5.5)로 이 Day06_new 자료를 만든 실제 작업과, 강사 기계의 실제 측정값으로 채운 예시다(2026-11-05).
> 숫자는 그날의 값이라 다시 재면 달라진다. 수강생은 **자기 칸을 먼저 쓴 뒤** 같은 칸끼리 비교한다.
> §3a와 §5b는 저자가 실험 폴더에서 Claude Code(Sonnet 5.5, 비대화형)를 한 번씩 돌린 관찰이다.

## §1 지금 내 흐름

예측: 산출물이 가장 먼저 빠진 단계는 Build일 것이다.

대상 작업: Day06 수업 목차를 받아 Claude Code 실습 자료(Day06_new)를 만든다.

| 단계 | 이 작업에서 한 일 | 남은 산출물 | 대화에만 남은 것 | 누가 판단했나 |
|---|---|---|---|---|
| Plan | 목차를 주고 GitHub 자료 조사를 맡겼다 | 없음(목차는 대화에 붙여 넣음) | 목차, "어떻게 가르칠지 고려하자"는 요청 | 나 |
| Design | 조사 결과와 Part별 교육 방식 제안을 받고 형식·스냅샷·세션 기록 사용·시간을 정했다 | auto memory 한 줄(`day06_ai_sdlc_outline.md`) | 제안 본문, 내가 고른 네 가지 결정 | 나 |
| Build | DAG와 노드 표로 된 제작 계획을 승인했다. Claude가 도구·카드를 만들었다 | 코드와 문서(worktree 브랜치), `docs/DESIGN.md` | **승인한 계획(DAG) 자체** — 대화에만 있었다. 나중에 `docs/DESIGN.md`로 옮겼다 | 계획은 나, 구현은 AI |
| Test | 결함별 반증 시험, 실제 세션 기록으로 도구 실행 | 시험 파일(강사 보관, git 제외) | 시험을 왜 그렇게 짰는지 | AI가 짜고 내가 기준(결함별 반증)을 정함 |
| Deploy | 아직 안 함(커밋 승인 전) | 없음 | — | — |
| Maintain | 아직 안 함 | 없음 | — | — |

예측과 실제: 예측대로 Build에서 처음 끊겼다. 승인한 계획이 파일이 아니라 대화에 있었다. 다음 세션은 그 계획을 읽을 수 없다.

## §3 Plan·Checkpoint·Evidence

예측: "이어서 작업해 줘"에 에이전트는 progress.md를 믿고 R4부터 할 것이다.

### §3a 실험 폴더에서 관찰한 것

- 처음 `check_evidence.py`: R1·R2·R7 오래된 증거, R3 거짓 통과 주장, R4·R6 미완, R5 미주장 통과, 완료 Gate 불통과(모델 호출 없이 확인)
- 저자 실측 1회(Sonnet 5.5, 비대화형): 첫 도구 호출 하나로 `progress.md`·`feature_list.json` 읽기, `git log`, 검사 실행을 했다(작업 규칙의 "시작할 때" 순서 그대로)
- R3 실패를 발견하고 R4로 가지 않았다. R3를 고쳐 코드 커밋(`73fa53f`) 뒤 `verified_at`을 그 해시로 적었다 → 두 번째 판정에서 R3 "일치"
- R1·R2·R7의 오래된 증거는 그대로 두었다("지금 코드에서도 통과한다"고 적기만 함) → 완료 Gate는 여전히 불통과
- 예측("R4부터")은 틀렸다. Checkpoint의 거짓을 끊은 것은 작업 규칙의 "시작할 때 검사 실행"이었다
- 깨뜨리기: hook이 검사 파일 편집을 막았다. 그런데 같은 차례에 함께 보낸 Bash가 실행되어 "검사를 바꿨다"는 **거짓 기록을 progress.md에 쓰고 커밋**했다. 에이전트가 스스로 발견해 `git revert`했다

### §3b 내 작업에서

| | 어디에 있었나 |
|---|---|
| Plan | 대화의 DAG와 노드 표. 파일은 나중에 `docs/DESIGN.md` |
| Checkpoint | auto memory 한 줄, git 브랜치. 대화 압축이 일어나면 계획 세부는 요약만 남는다 |
| Evidence | 시험 통과(그 시점 코드에 대한 것). 실측 전 비용 표는 "예고"로 표시 — 증거가 아니라는 표시 |

## §4 가져올 설계

## §5 내 계획 양식

### §5b 계획 비교 (저자 실측 1회, Sonnet 5.5, 비대화형)

| 칸 | 계획 A (plan mode) | 계획 B (칸을 정해 요청) |
|---|---|---|
| 1. 조사 | 있음. 검사를 실행하고 R3 실패를 "범위 밖, 보고만 함"으로 적음 | 있음. 요구사항별 통과·실패 표, R3 불일치 명시 |
| 2. 요구사항 연결 | R6 → R4 → R5 순서로 연결 | 작업마다 R# |
| 3. 바꿀 파일 | `reservation.py`만 | 작업마다 파일과 바꿀 위치 |
| 4. 먼저 실패할 검사 | 명시하지 않음(마지막 "검증"에 검사 이름) | 작업마다. R5는 "이미 통과해 먼저 실패를 볼 수 없다"고 밝히고 경계를 일부러 틀리게 바꿔 보는 확인을 제안 |
| 5. 통과의 뜻 | 검사 명령과 기대 결과("R3만 기존 실패로 남음") | 작업마다 명령과 기대 출력 |
| 6. 멈출 조건 | R3 처리만 "사용자 결정" | 작업마다(검사를 고쳐야 할 때, R3 동작을 바꿔야 할 때 등) |
| 7. 실행 주체와 사람 확인 지점 | 없음 | "이 세션에서 직접"과 이유(같은 함수, 순서 의존), 선택적 읽기 전용 검토 하위 에이전트 |

두 계획 모두 R4의 겹침을 **모든 사용자의 예약**에서 찾게 했다. 그래서 R3를 고치지 않고도 R4가 통과한다(저자가 직접 구현해 확인).

### §5c 내 업무의 계획에 반드시 넣을 칸과 실행 구조

반드시 넣을 칸: (1) 노드별 쓰기 범위 — 다른 세션이 같은 저장소를 고치고 있었다. (2) 노드별 자체 검증 — 결함별 반증. (3) 최종 감사의 통과·실패 기준.
실행 구조: 한 세션에서 차례로 하되, 웹 원문 대조처럼 독립적이고 읽을 양이 많은 노드만 하위 에이전트 세 개에 나눴다.
사람이 확인할 지점: 계획 승인, 유료 실측 직전, 커밋 직전.
