## M5-3. `[따라하기]` 계획 A: plan mode (6분, 유료)

터미널 2를 열어 실험 폴더에서 시작한다.

```bash
cd ~/day06-p5 && claude --permission-mode acceptEdits
```

폴더 신뢰 화면이 뜨면 읽고 수락한다. 그다음 `/plan` 뒤에 M5-1의 의도 문단을 붙여 보낸다(C7, K1).

```text
/plan <M5-1에서 쓴 의도 문단>
```

- plan mode에서는 계획을 승인하기 전까지 파일 편집이 막힌다(C7, X14). 계획이 나오면 **승인하지 않는다.** 실행할지 묻는 화면이 나오면 선택지는 셋이다: `1. Yes, and use auto mode` / `2. Yes, manually approve edits` / `3. Tell Claude what to change`. **3을 고른다**(승인하지 않고 계획을 계속 다듬는 선택지). 화면에 '아니오' 줄은 없다. Esc의 동작은 확인 필요다.
- 3을 고르면 Claude는 멈추고 입력창으로 돌아오며 plan mode가 유지된다. 파일은 바뀌지 않는다. 저자 확인 1회 (2026-11-06, 대화형, Claude Code 2.1.318).
- 계획 파일은 `~/.claude/plans/<세 단어로 된 이름>.md`로 새로 생기고, 승인 화면 아래쪽에도 이 경로가 표시된다 (저자 확인 1회 (2026-11-06, 대화형, Claude Code 2.1.318)). 터미널 1에서 가장 최근 파일을 실험 폴더로 복사한다.

  ```text
  !mkdir -p ~/day06-p5/plans && cp "$(ls -t ~/.claude/plans/* | head -1)" ~/day06-p5/plans/plan_a.md
  ```

- 편집이 막혔는지는 `!git -C ~/day06-p5 status --short`로 본다. 코드 파일이 `M`으로 나오지 않아야 한다. `plans/`는 `??`로 나온다.

## M5-4. `[따라하기]` 계획 B: 칸을 정해 요청한다 (6분, 유료)

터미널 2에서 `/clear`로 대화를 비운다. 이전 계획 A 때문에 plan mode가 켜져 있으면(상태 표시줄 `plan mode on`) Shift+Tab을 한 번 누른다. 그러면 auto 모드(`auto mode on`)로 나온다. 순환은 auto -> manual -> accept edits -> plan -> auto이다(저자 확인 1회 (2026-11-06, 대화형, Claude Code 2.1.318), 모드 플래그 없이 연 세션에서 관찰. acceptEdits로 연 세션에서의 순서는 시험하지 않았다). plan mode에서는 `plans/plan_b.md`를 쓸 수 없다. 그다음 아래 요청을 보낸다. 칸은 `part5/plan_template.md`에서 왔다. `<의도>` 자리에 M5-1의 문단을 넣는다.

```text
아래 의도를 구현하는 계획을 plans/plan_b.md 파일로 써 줘. 코드와 검사 파일은 고치지 마.
계획을 쓰기 전에 지금 상태를 확인해(검사를 실행해서 어떤 요구사항이 통과·실패하는지).
맨 위에는 조사 결과와 범위 밖을 적고, 작업마다 다음 칸을 넣어:
- 작업 ID와 연결 요구사항(R#)
- 바꿀 파일
- 먼저 실패하는 것을 확인할 검사 이름
- 통과의 뜻: 실행할 명령과 기대 결과
- 멈추고 사람에게 물을 조건
- 실행 주체: 이 세션에서 직접 / 작업마다 새 하위 에이전트
의도: <M5-1의 문단>
```

**관찰할 것.**

- 계획 B는 요청한 칸을 다 채웠나. 채우지 못한 칸이 있다면 그 칸은 누가 정해야 하나?
- 줄 수도 센다. 계획이 코드 본문을 담고 있다면 결정이 아니라 코드 초안이다.

## M5-6. `[내 것 만들기]` 검토자를 만든다 (4분)

하위 에이전트 정의는 프로젝트의 `.claude/agents/` 아래 마크다운 파일 하나다. 필드는 `description`(Claude가 언제 이 검토자에게 맡길지)과 `tools`(쓸 수 있는 도구)이고, `tools`를 빼면 모든 도구를 물려받는다(X2). 터미널 1에서 양식을 복사한다.

```text
!mkdir -p ~/day06-p5/.claude/agents && cp part5/reviewer_template.md ~/day06-p5/.claude/agents/reviewer.md
```

복사한 `~/day06-p5/.claude/agents/reviewer.md`를 열어 **두 빈칸을 내가 채운다.** 조교는 대신 정하지 않는다.

| 빈칸 | 정할 것 |
|---|---|
| `description` | 언제 이 검토자에게 맡길지 한 문장(X2) |
| `tools` | 검토자가 고치지 못하게 하려면 어떤 도구를 남기고 무엇을 뺄지(X2, T7). 양식의 "하는 일"에는 검사를 직접 실행하는 단계가 있다. 그 단계가 어떤 도구를 필요로 하는지도 함께 생각한다 |

- 필드 이름을 틀리게 쓰면(`tools`를 `tool`로) 오류 없이 무시되어 제한 없는 검토자가 된다(X2). 이름을 다시 읽는다.
- 이 파일은 `.claude/agents/` 아래에만 두면 된다. 터미널 2는 M5-7에서 `/clear`와 새 시작 어느 쪽이든 괜찮지만, 정의를 바꾼 뒤에는 새로 열어야 목록에 반영될 수 있다. 정확한 반영 시점은 확인 필요다.

## M5-7. 계획 → 구현 → 검토 (10분, 유료)

**먼저 예측하세요.** §5c의 예측 줄에 세 가지를 적는다.

- 검토자는 검사(`python3 -m unittest -v`)를 직접 실행할까?
- 검토자는 문제를 몇 개 찾을까?
- 검토자의 도구 호출이 내 표(`show_session.py`)에 보일까? 어디에 보일까?

그다음 터미널 2에서 새로 연 세션에 계획 B대로 구현을 시킨다. 새로 열 때도 같은 명령을 쓴다.

```bash
cd ~/day06-p5 && claude --permission-mode acceptEdits
```

```text
plans/plan_b.md대로 구현해 줘. 계획의 멈출 조건에 걸리면 멈추고 나에게 물어.
```

구현이 끝나면 이어서 같은 세션에서 검토를 맡긴다.

```text
reviewer 하위 에이전트로 지금 변경을 검토해 줘
```

터미널 1에서 두 가지를 읽는다.

```text
!uv run python tools/show_session.py --latest ~/day06-p5
!git -C ~/day06-p5 status --short
```

- `show_session.py` 맨 위 줄에서 권한 모드와 "하위 에이전트 정의 수"를 확인한다. 표 아래 "하위 에이전트" 구역에 `↳`로 시작하는 행이 검토자의 도구 호출이다(`tools/show_session.py:227`). 그 구역이 없다면 검토자가 불리지 않았거나 도구를 쓰지 않은 것이다. 무엇이었는지는 부모 표에서 `Agent` 호출 행이 있는지로 가른다. 행의 이름은 저자 실측(2026-11-06, 2.1.318)에서 `Agent`였다.
- `git status --short`에서 검토자가 파일을 고쳤는지 본다. 검토자가 `Edit`·`Write`를 갖고 있었다면 구현 변경과 검토 변경이 섞여 구별되지 않는다. 구현 변경만 `M`이어야 한다.
- 검토자는 별도 맥락에서 일하고 요약만 돌아온다(X3). 그 요약에 "확인한 것"과 "추정"이 나뉘어 있는지 읽고, 발견마다 `파일:줄`과 근거(실행 출력이나 diff)가 있는지 본다. 근거 없는 발견은 만들어 낸 것일 수 있다(I17).
- 검토자가 터미널 2 폴더의 CLAUDE.md를 읽고 시작했는지는 확인 필요다. 문서는 내장 Explore·Plan 에이전트만 말한다(X1).
- 검토자의 Bash 호출은 부모 세션의 권한 규칙으로 검사된다(T7). 승인 화면이 검토자 쪽에서 떴는지 적는다.

예측과 다른 칸에 **관찰**을 적는다. 이 관찰은 §5c에 쓴다: 검사를 돌렸나, 발견 몇 개 중 근거 있는 것은 몇 개, 표에 보였나, 파일을 고쳤나. 한 번의 관찰이므로 "1회 관찰"이라고 쓴다.

### §5d 내 업무의 실행 구조

계획과 검토를 내 업무에 옮긴다. `part5/plan_template.md`를 보고 §5d에 적는다.

- 내 업무의 계획에 **반드시** 넣을 칸 세 개와 이유
- 내 작업에 맞는 실행 구조 하나(한 세션 / 작업별 하위 에이전트 / 사람 배턴 / 게이트에서만 멈춤)와 이유
- 검토자를 둔다면 `description`과 `tools`에 무엇을 적을지
- 사람이 확인할 지점

작업마다 새 하위 에이전트를 쓰면 토큰이 곱해진다(X4). 비용만큼 값어치를 하는 경우인지 함께 적는다.

세션 두 개를 병렬로 돌리는 worktree와 `-p` 비용 칸, `/goal`은 강사 시연이다. 수강생은 이 미션에서 하지 않는다.
