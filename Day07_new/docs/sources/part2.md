# Part 2 근거 대장

Part 2(KV Cache) 강의 노트북이 인용할 사실만 모은 대장이다. 코드 근거는 vLLM v0.32.0(commit 5df63a7) 소스 루트 기준 `경로:줄`이고, 인용한 줄은 모두 열어 확인했고, 2026-11-02에 모든 행을 원문과 호출 경로로 다시 대조했다. 블로그는 절 제목만 적는다. 블로그의 예시 request와 문장은 옮기지 않고 모두 다시 풀어 썼다. 공식 문서는 같은 소스 트리의 `docs/` 파일이고, PR과 이슈의 상태는 2026-11-01에 `gh`로 읽은 값이다.

상태 정의: 일치(블로그·문서·코드가 같은 말), 문서·코드 차이(문서가 코드보다 낡음), 블로그·코드 차이(블로그 서술이 v0.32.0 코드와 다르거나 일부만 맞음), 코드 전용(블로그에 없고 코드에서만 확인), 미확인(이 노드에서 근거를 못 봄).

## GLM-5.3-Flash KV 구조

근거 위치는 `vllm/models/glm5next/`다(model class 이름은 `Glm5Next`, 블로그와 같다). 읽은 범위는 `common/model.py`, `common/attention.py`, `common/kda.py`와, 이들이 상속하는 `mla_attention.py`·`mamba/abstract.py`의 `get_kv_cache_spec`다.

층 종류와 KV spec은 네 가지다.

| 층(코드 이름) | 어떤 KV spec | 근거 |
|---|---|---|
| 선형 attention 층(`Glm5NextLinearAttention`, KDA) | `MambaSpec`: token마다 쌓이는 KV가 아니라 request당 고정 크기 state. 메모리 상한은 `page_size * (1 + num_speculative_blocks)`(align 모드는 `page_size * (2 + num_speculative_blocks + num_prefill_checkpoint_blocks)`)로 문맥 길이 T를 포함하지 않는다. | `vllm/models/glm5next/common/kda.py:163-176`(`:163`이 클래스, `:168`이 `get_kv_cache_spec`), `vllm/model_executor/layers/mamba/abstract.py:65-84`, `vllm/v1/kv_cache_interface.py:1035`, `:1076-1082` |
| sparse(MLA) attention 층(`Glm5NextMLAAttention`) | `MLAAttentionSpec`: KV head 1개, `head_size = kv_lora_rank + qk_rope_head_dim`, 별도 V 없음(`head_size_v = 0`)이라 K·V 2배 항이 없다. token당 byte는 `kv_cache_dtype`에 달렸다. `fp8_ds_mla`는 656, `nvfp4_ds_mla`는 352로 고정이라 head_size로 계산하지 않는다. indexer가 있으면 `is_index_group_leader`가 켜진다. | `vllm/models/glm5next/common/attention.py:385`, `:554-565`, `vllm/model_executor/layers/attention/mla_attention.py:479`, `:1350-1380`(dtype별 byte는 `:1365`), `vllm/v1/kv_cache_interface.py:686-698` |
| MLA 층에 붙은 indexer K cache(`Glm5NextIndexerCache`) | `MLAAttentionSpec`에 `tokens_per_state = index_kpool`을 지정한 것: kpool 압축으로 `index_kpool` token마다 state 하나를 저장하므로 block 안의 state 수가 `block_size / index_kpool`로 줄어든다. 값은 uint8 + `quant_block_size`(128)개당 fp32 scale. | `vllm/models/glm5next/common/attention.py:79-122`, `:253`, `:260-266`, `vllm/v1/kv_cache_interface.py:231-233` |
| MLA 층에 붙은 tail cache(`Glm5NextTailCache`) | `CircularBufferSpec`: request당 block 하나짜리 링 버퍼(미완성 꼬리 pool의 원본 K와 gate score를 bf16으로 보관). ring 크기는 `index_kpool`과 `num_speculative_tokens`로 정해져, 문맥이 길어져도 크기가 늘지 않고 prefix caching 대상이 아니다. | `vllm/models/glm5next/common/attention.py:125-181`, `:271-277`, `vllm/v1/kv_cache_interface.py:909-946` |

어느 층이 KDA이고 어느 층이 MLA인지는 `config.layer_types[layer_idx] == "linear_attention"`으로 정해진다(MTP 층은 항상 MLA). 이 값의 실제 배열은 HF 설정 파일 `https://huggingface.co/zai-org/GLM-5.3-Flash/raw/main/config.json`의 `text_config`에서 읽었다(2026-11-02, 값의 상세 근거는 `part7.md` P7-41~P7-44). 전체 45층 중 `linear_attention`이 34층, `deepseek_sparse_attention`이 11층이고, `kv_lora_rank`는 512, `qk_rope_head_dim`은 0, `index_kpool`은 4다. transformers 문서의 `index_kpool` 기본값 16은 이 체크포인트의 값이 아니다. 소스의 FLASHMLA_SPARSE 주석이 GLM5Next NoPE 경우의 `kv_lora_rank == 512`를 적는데(`vllm/v1/attention/backends/mla/flashmla_sparse.py:220-221`) config 값과 같다. 근거: `vllm/models/glm5next/common/model.py:130-136`, `:370-371`.

원식 `2*B*L*T*n*d*b`(요청 B개, 층 L, 토큰 T, KV head n, head 차원 d, dtype 바이트 b)는 GLM-5.3-Flash에 그대로 적용할 수 없다. 이유는 여섯 가지다.

1. KDA 층에는 T 항이 없다. request당 상수 state이므로 식의 L에 선형 층을 세면 틀린다.
2. MLA 층에는 2가 없다. K와 V를 따로 두지 않고 잠재 벡터 하나만 둔다(`head_size_v = 0`). n은 1이고 d는 `kv_lora_rank + qk_rope_head_dim`이다.
3. MLA 층마다 indexer cache가 따로 있고, 이쪽은 `index_kpool` token당 state 하나라서 T에 비례하되 계수가 다르다.
4. tail cache는 request당 고정 크기 링 하나가 더 붙는다.
5. hybrid pool은 group 크기를 맞추려고 padding layer를 넣거나 page를 padding하므로(P2-61, P2-62) 실제 점유는 이론식보다 클 수 있다.
6. MLA 층의 token당 byte는 `head_size * dtype`이 아닐 수 있다. `fp8_ds_mla`와 `nvfp4_ds_mla`는 고정값(656, 352)이다(`mla_attention.py:1365`). 어느 dtype이 쓰이는지는 `kv_cache_dtype`으로 정해지고 이 대장은 확정하지 않는다.

식이 근사로라도 맞는 것은 "일반 full attention 층만 있는 model"(P2-05의 page 식을 층·block 수로 곱한 값)이다. 따라서 수업에서 GLM-5.3-Flash의 KV 용량을 계산할 때는 층 종류별로 따로 더해야 하고, 숫자는 위 config 값(34층 선형, 11층 sparse, `kv_lora_rank` 512, `index_kpool` 4)에서 가져온다.

참고: RFC #58638 본문은 "GLM-5.3-Flash + DFlash2 조합은 PR 적용 전후 grouping이 같아 영향이 없다"고 적는다. 이것은 이슈 작성자의 주장이고 이 노드에서 코드로 재현하지 않았다(미확인).
