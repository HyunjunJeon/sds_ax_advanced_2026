# Part 6 근거 대장

Part 6은 Tool Calling 오류와 수정이다. 아래 주장은 vLLM v0.32.0 소스(커밋 5df63a7)를 **읽어서** 확인한 것이 기본이다. 일부 행은 실제 코드를 사람이 만든 문자열로 실행한 기록을 함께 인용한다. Python 파서와 serving 제너레이터(`Day07_new/data/reference_parser_stream.json`, `Day07_new/docs/reference/parser_stream.md`), Rust 파서 crate(`Day07_new/data/reference_parser_rust.json`, `Day07_new/docs/reference/parser_rust.md`), GLM 구조화 태그의 xgrammar 입력 시험이다. 엔진, 모델, 서버는 돌리지 않았다. 그래서 "무엇이 일어난다"는 서술은 코드 읽기이거나 구성 문자열 실행이며, 실제 응답으로 확인되기 전까지 강의에서 "서버에서 관찰했다"고 말하면 안 된다.

표기 규칙은 다음과 같다.

- 코드 경로는 `vllm/...:줄`이다. 별도 표시가 없으면 v0.32.0 소스 저장소 기준이다. `rust/...`는 같은 저장소의 `rust/` 아래다.
- 공식 문서 열은 소스 저장소 안의 `docs/features/tool_calling.md:줄`(이하 `docs:줄`)과 레시피 사본 `recipe-glm53.txt:줄`을 쓴다.
- 블로그는 절 제목으로만 가리킨다. 블로그 제목은 "Inside vLLM: 서버 시작부터 KV cache까지 소스 코드 톺아보기"다.
- 상태는 일치, 문서·코드 차이, 블로그·코드 차이, 코드 전용, 미확인 중 하나다.

## 적용 범위 전제

이 대장의 Python 경로 행은 **Python frontend**(기본값) 기준이다. `VLLM_USE_RUST_FRONTEND`의 기본값은 꺼짐이다(`vllm/envs.py:1475-1477`). 그런데 GLM-5.3-Flash 레시피는 명령에 `VLLM_USE_RUST_FRONTEND=1`을 넣는다(`recipe-glm53.txt:17`). Rust frontend는 파서를 따로 구현하고 Python 파서와 동작이 다르다(P6-04, P6-29, P6-30). Day07 Pod가 어느 frontend로 떠 있는지는 이 대장에서 확인하지 못했다.

## 권장 서버 플래그와 근거

GLM-5.3-Flash로 Tool Calling을 쓰는 서버의 최소 플래그는 다음 셋이다.

- `--tool-call-parser glm47`: 레시피 명령에 있다(`recipe-glm53.txt:22`). 레지스트리에 이름이 있다(`vllm/tool_parsers/__init__.py:65-67`).
- `--enable-auto-tool-choice`: 레시피 명령에 있다(`recipe-glm53.txt:23`). 이 플래그를 주고 위 플래그를 안 주면 시작이 실패하고(`vllm/entrypoints/launchers/cli_args.py:523-524`), 반대 경우는 도구 파서가 None이 되고, `tools`를 실은 요청은 오류 응답을 받는다(`vllm/parser/parser_manager.py:36-37`, `online_renderer.py:253-270`). `tools`가 없는 요청만 조용히 통과한다.
- `--reasoning-parser glm47`: 레시피 명령에 있다(`recipe-glm53.txt:24`). 생각이 항상 켜진 모델이라서(`recipe-glm53.txt:138`) 이 플래그가 없으면 구조화 출력 쪽 reasoner도 비게 된다(P6-23).

선택 플래그는 다음과 같다.

- `--tool-strict-level parameter`: 모든 도구의 인자 스키마까지 고정한다(`docs:143-157`, `vllm/entrypoints/launchers/cli_args.py:131-137`). GLM은 기본이 `function`이라서 껍데기 제약과 얕은 태그는 이미 켜져 있다(P6-12, P6-27). 이 값이 더하는 것은 스키마 고정이고, xgrammar 시험에서 필수 인자 누락(C5)을 막는 쪽이 strict 태그였다. 서버 재시작이 필요한 비교 실험과 엔진 집행은 실행하지 않았다.
- `--exclude-tools-when-tool-choice-none`: `tool_choice="none"`일 때 프롬프트에서 도구 정의를 뺀다(`docs:107-110`).

피해야 할 설정은 `VLLM_ENFORCE_STRICT_TOOL_CALLING=0`이다. GLM에서는 required/named의 유일한 제약이 사라진다(P6-26).

레시피는 `VLLM_USE_RUST_FRONTEND=1`과 `--tokenizer-mode glm5_next`도 기본 명령에 넣는다(`recipe-glm53.txt:17-19`). 뒤의 값은 고정한 v0.32.0에서 받아들여지지 않는 값으로 읽힌다(P6-35). 이 두 개는 Tool Calling 플래그가 아니고, Day07 Pod가 어떤 명령으로 떴는지는 이 대장에서 확인하지 못했다. 그 명령을 확인하기 전에는 Python 파서 행(P6-16 ~ P6-19)을 Pod 동작으로 단정하지 않는다.

## 수업에 쓰지 말 것

- `hermes_tool_parser.py`의 동작을 GLM 동작처럼 설명하지 않는다. GLM은 `glm47_moe_tool_parser.py`와 `vllm/parser/glm47_moe.py`를 통한다.
- 위 "실패 사례 후보"를 서버에서 관찰된 사실처럼 쓰지 않는다. 구성 문자열 실행이 있는 사례도 "이 문자열을 넣으면 파서가 이렇게 낸다"까지만 말한다. 모델이 그 문자열을 낸다는 뜻이 아니다.
- 응답 필드를 `reasoning_content`라고 가르치지 않는다. v0.32.0 응답은 `reasoning`이다(P6-31).
- "required/named는 JSON 스키마로 항상 파싱 가능한 호출을 보장한다"는 문서 문장(`docs:88-103`)을 GLM에 그대로 적용하지 않는다(P6-07).
- "auto는 `strict`가 없으면 제약이 없다"는 문장을 GLM에 적용하지 않는다(P6-12).
- `glm45`와 `glm47` 사이에 Python 서버에서 동작 차이가 있다고 말하지 않는다. 같은 클래스다(P6-01, P6-02). 서버 수준에서 Rust frontend의 차이와 혼용 안전성은 확인되지 않았다(P6-04).
- Rust frontend의 잘린 호출 처리와 선언되지 않은 도구 이름 처리를 Python과 같다고 말하지 않는다(P6-29, P6-30). Rust 파서 오류가 HTTP 오류로 나간다고도 말하지 않는다. 코드는 text로 되돌린다(P6-30, 실행 안 함).
- 잘린 호출이 "버려진다"고 단정하지 않는다. 소스 주석은 그렇게 쓰지만(`vllm/parser/abstract_parser.py:474-481`), 이름이 맞는 부분 호출은 살아남는다(P6-16, 구성 문자열 실행).
- 스트리밍과 비스트리밍의 `finish_reason`이 같다고 가르치지 않는다(P6-14, P6-15).
- `--tokenizer-mode glm5_next`가 v0.32.0에서 그대로 된다고 말하지 않는다(P6-35, P1-49).
- 서버가 필수 인자나 타입을 검증해 준다고 말하지 않는다. 파서에서 확인되지 않았고(P6-18), 기본 얕은 태그도 필수 키 누락을 통과시켰다(P6-27). 검증은 클라이언트 몫으로 설계하는 편이 안전하다.
- `tools: []`면 이름 검사를 안 한다고 말하지 않는다. 요청 검증에서 거절된다(P6-17).
