# Part 8 근거 대장: LMCache를 포함한 KV cache 운영

vLLM KV cache를 운영할 때 어떤 경로를 어떤 플래그로 켜는지, 무엇이 시작을 막는지, 실패하면 무슨 일이 생기는지를 코드 호출을 따라가 모은 대장이다. 이 대장의 "~한다"는 코드와 문서를 읽은 결과다. 예외는 `실제 클래스 호출`로 표시한 칸과 P8-04, P8-05, P8-09, P8-15, P8-19의 보정이고, 이것들은 CPU에서 실제 vLLM과 LMCache 클래스를 호출한 결과다(`docs/reference/lmcache.md`). vLLM이나 LMCache 서버에 모델을 올려 돌린 결과는 하나도 없다.

근거 트리는 둘이다. vLLM은 v0.32.0(commit 5df63a7) 소스 루트 기준 `경로:줄`이다. LMCache는 2026-11-02 기준 최신 정식 릴리스인 v0.5.6(commit `3e11e10812b448142c6cdb177a3058652bd826fa`, 커밋 시각 2026-10-12, 릴리스 게시 2026-10-14)이고, `v0.5.7rc*`와 `nightly*` 태그는 시험판이라 고르지 않았다. 표에서 `LMCache:`를 앞에 붙인 경로는 전부 이 트리 기준이다. 이 소스는 GPU 확장 없이(`NO_GPU_EXT=1`) 빌드해 CPU에서 게이팅 관문, SCHEDULER 역할 생성자, 가짜 텐서 저장만 실행했다. PyPI wheel은 macOS에서 `cupy-cuda13x` wheel이 없어 설치되지 않았다. 표의 `v0.32.0 코드` 열에는 두 트리의 코드를 함께 적는다. 블로그는 이 Part의 근거가 아니므로 `블로그 절` 열은 모두 `—`이다. PR, 이슈, 레시피, 논문은 2026-11-02에 `gh`와 웹으로 읽은 값이다. 레시피는 `recipes.vllm.ai/<모델>.md` 렌더링이며 절 이름으로 가리킨다. 문서 페이지 `docs.vllm.ai/en/stable`은 읽은 날 v0.33.0을 가리켰으므로, 같은 내용은 v0.32.0 트리의 파일로 인용한다.

## 수업에 쓰지 말 것

조건을 떼어 낸 배수와 낡은 문구다. 쓰려면 조건을 함께 적고 자기 보고라고 밝힌다.

1. LMCache 논문의 "최대 15배"를 그대로 쓰기. 본문 범위와 조건은 P8-53에 있고, 비교 대상은 v0.32.0이 아니다.
2. LMCache 블로그 제목의 "10배"(2026-04-03). 표의 숫자는 평균 TTFT 약 13배, p99 10배 초과, 디코드 약 4배로 지표마다 다르고, 조건은 Qwen3-235B-A22B-FP8, 8×H100 80GB, vLLM 0.18.1, LMCache 0.4.3-dev, DP 8개, `--disable-hybrid-kv-cache-manager`를 준 프로세스 내 기준선, `lmcache bench`의 다중 라운드 대화다. 벤더 자체 벤치마크이고 P/D, 다중 노드는 로드맵으로 적혀 있다.
3. ATOM PR의 처리량 +20.5~32.6%. 각 칸 n=1이고 오차 막대가 없으며, 고정 prefix 풀이 높은 동시성에서 hit 쪽으로 치우친다고 PR이 스스로 적는다. 정확도(GSM8K)도 주장하지 않는다.
4. DeepSeek-V4-Flash 레시피의 cold-warm TTFT 6.6배(LMCache: `docs/source/recipes/deepseek_v4_flash.rst:118-119`). 프롬프트 조건이 없고 가장 유리한 cold 비교다.
5. GLM-5.3 레시피의 외부 hit률 40.6%와 48.3%. 5040 token 프롬프트 하나의 chunk 정렬 비교이고 chunk 크기 원리 설명 용도로만 맞다.
6. vllm#38230의 79%, 97%, 1061 tok/s. 포크 브랜치의 Qwen3.5이고 v0.32.0 근거가 아니다(P8-40).
7. "LMCache가 GLM-5.3-Flash를 검증했다". 검증 대상은 `zai-org/GLM-5.3`이고 레시피가 `-Flash`를 제외한다(P8-26, P8-27).
8. "MP connector는 `--disable-hybrid-kv-cache-manager`가 필요하다". 내장판 얘기이고 hybrid 모델이면 시작이 멈춘다(P8-15, P8-17).
9. "`--kv-offloading-size`가 LMCache 용량을 정한다". `lmcache` backend에서는 connector로 넘어가지 않는다(P8-03).
10. "`--no-enable-prefix-caching`은 LMCache의 권장 설정이다". GLM-5.2 레시피의 선택이고, Mamba 모델이면 거부된다(P8-29).
11. "LMCache 쪽 hit률을 `vllm:` 지표로 계층별로 볼 수 있다". 모두 `external_unspecified`다(P8-36).
12. Kimi-K3의 block 크기를 하나의 숫자로 말하기. 768과 1536은 TP, 하드웨어, 경로가 다른 값이다(P8-20).

## 못 읽은 것

- 실행: 모델을 올린 vLLM 서버와 GPU는 쓰지 않았다. 게이팅 관문과 SCHEDULER 생성자 호출, 가짜 텐서 저장 말고는 `SupportsHMA` 판정부터 복원까지 읽기만 했다. worker 역할 connector, `FLASHINFER_MLA` 같은 GPU 백엔드, `--separate-object-groups`의 block 분할, FlashKDA checkpoint 저장·복원(P8-26)은 실행하지 않았다.
- `vllm-router`와 `vllm-project/production-stack`은 이 트리 밖이라 cache-aware routing 알고리즘을 읽지 못했다(P8-44).
- ATOM의 `recipes/atom_vllm/Kimi-K3-LMCache-Byte-Offload.md`와 커넥터 코드는 읽지 않았다. PR 본문만 읽었다.
- LMCache의 L2 어댑터 구현, CacheBlend 엔진 내부, `lmcache/v1/distributed/bitmap_ops/fold.py`의 `fold_grouped` 본문은 읽지 않았다. 함수 설명과 호출부까지만 봤다.
- 내장 `lmcache_integration/multi_process_adapter.py`가 `LMCacheMPConnectorUpstream`의 `cache_salts` 인자를 받는지는 grep에서 `salt`가 나오지 않았다. 내장판 단독 경로의 salt 처리는 확인이 필요하다.
- LMCache #2879, #2845는 vllm#38230 본문의 언급만, vLLM PR #62424는 GLM-5.3-Flash 레시피의 언급만 봤다. 본문을 읽지 않았다.
