## 01-Serving-Basics

### 절 0. 요청 한 건의 지도 (4분)

> 보일 셀: 2번(수업 서버와의 차이), 3번(정거장 표), 4번(프로세스별 그림)

오늘은 요청 한 건이 서버 안에서 모양을 바꾸며 지나가는 길을 한 번 걷습니다. 세부보다 어디서 무엇이 결정되는지만 잡아 주세요.
먼저 약속입니다. 기준은 vLLM 0.32.0 소스이고, 우리는 이 소스로 서버를 띄운 적이 없습니다. 그래서 오늘 제 말은 코드에 이렇게 적혀 있다, 또는 클래스를 불러 보니 이렇게 나왔다는 뜻입니다. 우리 수업 서버가 이렇게 돈다는 뜻이 아닙니다. 수업 서버는 더 이른 빌드이고, 어떤 frontend로 떠 있는지도 아직 모릅니다.
표를 보세요. 정거장이 아홉 개 있고, 지금은 객체 칸과 어디서 칸만 눈에 익히면 됩니다. 프로세스는 API server, EngineCore, GPU worker 세 종류입니다. 정거장 번호는 vLLM에 없는 말이고, 수업이 코드를 읽고 붙인 번호입니다.
그리고 대화의 다음 턴은 이어 붙이기가 아닙니다. client가 대화 전체를 담은 새 요청을 보내서 정거장 1부터 다시 시작합니다. 이 사실이 왜 값진지는 05에서 드러납니다.
아래 그림은 같은 표를 프로세스별로 다시 그린 것입니다. 화살표는 프로세스를 건너는 곳에만 있고, 7번에서 5번으로 돌아가는 고리는 그리지 않았습니다.

### 절 1. step: 실행의 단위 (8분)

> 보일 셀: 6번(step 표와 뼈대 코드)

실행의 단위는 요청이 아니라 step입니다. EngineCore는 요청을 하나씩 끝까지 처리하지 않습니다. step 함수 하나가 같은 네 동작을 차례로 합니다. schedule, execute_model, sample_tokens, update_from_output입니다. sample_tokens는 execute_model이 None을 돌려줄 때만 부르는데, 이유는 절 6에서 봅니다.
핵심 문장은 이겁니다. scheduler에는 prefill 단계도 decode 단계도 없습니다. 요청마다 숫자가 두 개뿐입니다. 계산을 끝낸 token 수, 그리고 draft까지 센 전체 token 수입니다. scheduler는 매 step 앞의 숫자가 뒤의 숫자를 따라잡도록 예산 안에서 token을 나눠 줍니다. 그래서 프롬프트 조각과 답 token이 한 step에 섞입니다. prefill, decode는 그 차이의 크기에 우리가 붙인 이름일 뿐입니다.
예외가 하나 있습니다. DP prefill balancing이 일부 step을 늦출 때는 진행 중인 prefill 조각을 미룹니다. 이 설명은 공식 문서에 없고, 코드 주석이 근거입니다.

> 보일 셀: 7번(수업용 모델 경고), 8번(모델링하지 않은 것)

이제 수업용 모델로 관찰합니다. 중요합니다. 이것은 vLLM이 아니라 수업용 모델입니다. 규칙을 한 프로세스, 선착순으로 옮겨 적은 교육용 코드이고, 모델링하지 않은 것은 첫 셀이 출력합니다. 실제 Scheduler 클래스를 CPU에서 돌린 기록과 대조했지만, 그건 서버 관찰이 아니라 클래스 호출입니다. 시각은 선언한 toy 상수이고 측정이 아닙니다.
[예측] doc의 프롬프트는 54 token, 한 step의 예산은 32입니다. doc의 첫 출력 token은 몇 번째 step이 끝날 때 나옵니까? 종이에 적으세요.

> 보일 셀: 10번(표 실행), 12번, 14번(그림)

표를 위에서 아래로 읽습니다. 한 행에 요청이 여럿 들어간 step이 어디부터인지 찾아 보세요. 방금 말한 대로 prefill token, decode token 칸은 이 수업 모델이 붙인 분류입니다. 그림은 같은 결과를 요청별로 펼친 것이고 폭은 toy 시간입니다.

### 절 2. 프로세스 경계 (8분)

> 보일 셀: 16번(프로세스 세 종류, AsyncLLM 표)

프로세스는 세 종류입니다. API server는 HTTP를 받고 입력을 token으로 바꾸고 출력 token을 글자로 되돌립니다. EngineCore는 scheduler와 KV 관리를 쥐고 busy loop를 돕니다. GPU worker는 weight를 올리고 forward를 돌립니다. GPU가 하나뿐이면 worker가 EngineCore 프로세스 안에서 돕니다.
앞의 둘 사이 통신은 ZMQ이고, 그래서 정거장 3과 7의 객체는 직렬화할 수 있는 구조체입니다. API server 안에서는 AsyncLLM이 renderer, InputProcessor, OutputProcessor, EngineCore client 네 가지를 만듭니다.
EngineCore는 worker가 몇 개이고 어디 있는지 모릅니다. executor의 collective_rpc에 메서드 이름만 넘깁니다. 그래서 step 코드가 GPU 수와 무관하게 같습니다.
worker 수는 PP(pipeline parallel), TP(tensor parallel), PCP(prefill context parallel)의 곱이고 DP(data parallel)는 곱하지 않습니다. 수업 서버 구성은 H200 네 장, TP4에 MTP 5입니다. 레시피 기본은 아니고, 수업 서버의 KV dtype은 이 자료로 확인되지 않았습니다.

> 보일 셀: 17번(world_size 표), 18번, 19번(프로세스 표), 20번 끝의 표

관찰할 것은 DP가 있는 마지막 행입니다. EngineCore당 worker와 전체 worker를 비교해서, DP가 어느 칸의 곱에 들어가고 어느 칸에는 안 들어가는지 말해 보세요.
아래 표는 문서와 코드가 다른 곳입니다. 문서는 worker 수를 TP 곱하기 PP라고 하지만 코드는 PCP까지 곱합니다. 이런 경우 코드가 맞습니다. AsyncLLMEngine도 파일이 별칭 한 줄이고 구현은 v1 엔진 폴더에 있습니다.

> 보일 셀: 21번(왜 이렇게 설계했나)

분리의 출발은 RFC 이슈입니다. 통신 수단을 비교한 PR의 수치는 그 작성자가 그 조건에서 잰 값이라 우리 모델과 구성에 옮길 수 없습니다. 구조 자체는 코드로 확인한 사실입니다.

### 절 3. 서버 초기화 순서 (11분)

> 보일 셀: 22번(예측 문제), 23번(순서 표)

요청이 지나갈 길은 서버가 시작할 때 만들어집니다. 프로세스, 소켓, KV 크기가 여기서 정해지니 순서를 알면 시작 실패 로그를 읽는 법이 달라집니다.
[예측] 포트 bind, 엔진 초기화, HTTP route 등록 중 무엇이 가장 먼저이고 무엇이 가장 나중입니까? 이유를 한 문장으로 적으세요.
표를 보고 답을 맞춰 봅니다. 이 호출 순서를 줄 단위로 설명한 공식 문서는 찾지 못했고, 코드를 따라 읽은 것입니다.

> 보일 셀: 24번(구간 1에서 3)

여섯 구간으로 걷습니다. 구간 1은 모드 선택입니다. vllm serve가 실행 모드를 고르고, 아무 분기에도 안 걸리면 이 프로세스에서 run_server를 돌립니다. 구간 2가 핵심입니다. run_server 안에서 setup_server가 먼저 소켓을 잡고, 바로 다음 줄이 그 소켓을 들고 엔진을 만들러 갑니다. listen이 걸리는 위치는 경로마다 다릅니다. API server가 하나면 Uvicorn 안이고, 여러 서버가 소켓을 공유하는 경로에서는 vLLM이 직접 부릅니다. 구간 3은 설정이고, 기본값 결정과 검증은 create_engine_config에서 일어납니다.

> 보일 셀: 25번(구간 4에서 6)

구간 4는 client와 handshake입니다. 대화는 세 번 오갑니다. EngineCore가 HELLO, client가 소켓 주소, EngineCore가 READY입니다. 이 대기에는 시간 한도가 없고 프로세스가 죽으면 바로 깨어납니다.
구간 5가 무겁습니다. 순서는 executor, KV cache, scheduler입니다. worker가 메모리 예산을 정합니다. 예산은 gpu_memory_utilization 곱하기 GPU 전체 메모리이고, 기본 비율은 0.92입니다. 연산 사용률이 아니라 메모리 비율입니다. 그다음 profile_run이 최대 token 수 크기의 dummy 입력을 돌려 activation 최고치를 잽니다.
그래서 KV 크기는 시작할 때 실제로 모델을 돌려 본 결과로 정해집니다. 예외는 kv-cache-memory-bytes를 직접 주는 경우입니다.
구간 6, READY를 받은 뒤에야 HTTP route를 붙이고 Uvicorn을 띄웁니다. 구간 2에서 잡아 둔 그 소켓을 넘깁니다.

> 보일 셀: 27번(시간이 아니라 순서), 29번(실패 재현), 31번(bind 위치 표)

칸 너비는 모두 같습니다. 시간이 아니라 순서입니다. 구간별 소요 시간은 이 자료에 없고, 강사 메모의 15분에서 20분은 다른 빌드에서 한 번 잰 값입니다.
실패 재현입니다. 같은 포트를 소켓 두 개로 bind합니다. 오류 번호가 운영체제마다 다를 수 있으니 어느 칸이 달라지고 어느 칸이 같은지 보세요. 이 표는 단계 수를 센 것이고, 숫자의 뜻은 실패를 알기까지 weight를 올리고 profiling을 돌렸는가입니다.

> 보일 셀: 32번(시작 로그 읽기), 33번

시작 로그의 KV 용량 줄은 profiling이 끝난 뒤, 남은 초기화 전에 찍힙니다. 세 숫자는 독립이 아니라 N을 M으로 나누면 X가 나와야 합니다. PDF의 예시 로그는 설명용이라고 밝혔는데 세 숫자가 이 관계를 만족하지 않습니다. 나중에 진짜 로그를 보면 같은 산수로 검산하세요.

### 절 4. request 경로와 객체 사슬 (11분)

> 보일 셀: 36번, 37번(객체 사슬 표), 38번 앞부분

이 표가 이 노트북에서 가장 중요합니다. 요청은 층을 지날 때마다 다른 객체로 바뀌고, 각 객체는 그 층이 알아야 할 것만 듭니다. ChatCompletionRequest, EngineInput, EngineCoreRequest, Request, SchedulerOutput, ModelRunnerOutput, EngineCoreOutputs, RequestOutput 여덟 개입니다. 3번과 7번이 ZMQ 경계를 넘습니다. 객체 사슬을 한 표로 정리한 공식 문서는 찾지 못했습니다.
정거장 1과 2에서 기억할 것은 tokenize가 API server 프로세스의 일이라는 점입니다.

> 보일 셀: 38번(생성 한도 표), 39번

생성 한도는 네 항의 최솟값입니다. 모델 최대 길이에서 입력 길이를 뺀 값, 요청이나 서버 기본 값, 생성자가 미리 고른 값, 플랫폼 한도입니다. 일부 항은 함수 밖에서 정해집니다. 아래 셀의 숫자는 수업이 정한 값입니다.

> 보일 셀: 40번, 41번(ADD 순서 표), 42번

정거장 3과 4는 순서가 중요합니다. 결과 queue를 먼저 등록하고 나서 보냅니다. 큐 한도는 기본이 둘 다 None이라 설정하지 않으면 거절하지 않고, 설정하면 넘는 요청을 HTTP 503으로 돌려보냅니다. 그리고 이 검사는 chat 경로에서 두 번 불립니다. render 앞에서 한 번, ADD 직전에 한 번이라 한도를 넘은 요청은 보통 tokenize 전에 거절됩니다.

> 보일 셀: 43번(실패 재현), 44번

이 셀은 수업용 모사입니다. vLLM 코드를 부르지 않고 한도 비교와 메시지만 옮겼습니다. 세 줄 중 예외가 난 줄의 상태 코드와 메시지의 마지막 구절을 읽으세요. client에게 무엇을 하라고 합니까? 한도가 없으면 요청은 어디에 쌓입니까?

> 보일 셀: 44번 아래쪽(정거장 5에서 7), 44번 끝의 종료 원인 표

정거장 5에서 7입니다. schedule은 running을 먼저 처리하고, block을 받았을 때만 예산을 차감합니다. block을 못 받으면 낮은 우선순위 요청을 되풀이해 preempt하고, 자기 차례가 오면 자기를 내보냅니다. block을 어떻게 받는지는 일부러 비워 둡니다. 02a의 주제입니다.
끝을 판단하는 쪽은 둘로 나뉩니다. EOS와 max_tokens는 token 수나 ID로 알 수 있으니 EngineCore가, stop string과 연결 끊김은 글자와 HTTP 연결을 쥔 API server가 판단해서 abort를 보냅니다. 끝난 요청은 block을 반납하는데, 이때 KV 값은 지우지 않습니다. 이 뒤쪽은 02b에서 봅니다.

### 절 6. Model Runner V2와 async scheduling (5분)

> 보일 셀: 54번(MRV2 개념과 표)

절 1에서 None을 검사한 이유가 여기 있습니다. MRV2는 forward 뒤 hidden state를 저장해 두고 마지막 PP rank에서 None을 돌려줍니다. 그러면 EngineCore가 sample_tokens를 따로 부르고, 그래서 정거장 6이 호출 두 번으로 나뉩니다. 공식 문서는 MRV2가 아직 기능이 완전하지 않고 충분히 시험되지 않았다고 적습니다.

> 보일 셀: 54번 코드 문단, 55번

어느 runner를 쓸지는 조건으로 갈립니다. 환경변수에 값이 있으면 그 값이 우선하고, 비어 있으면 Triton이 있고 미지원 기능이 없을 때 V2입니다. 아니면 V1 runner입니다.

번호가 세 종류 나옵니다. position은 요청 안에서 몇 번째 token인가이고, block ID는 pool 전체에서 하나이며, slot은 worker가 계산하는 KV cache 전체의 번호입니다. scheduler는 block ID까지만 다룹니다. slot은 worker에서 처음 생깁니다.
주의할 점이 있습니다. 이 노트북은 attention 종류가 하나인 경우만 다룹니다. GLM-5.3-Flash는 층 종류가 여럿이라 그대로 대입할 수 없고, 그 이야기는 02b에서 합니다.

### 절 1. KV가 왜 필요한가 (5분)

> 보일 셀: 5번

attention은 token 하나를 계산할 때 앞선 token의 K와 V를 읽습니다. 보관해 두지 않으면 매번 문맥 전체를 다시 넣어야 합니다. KV cache는 이미 계산한 K와 V를 GPU에 두고 다시 읽게 하는 저장소입니다.
연산량 공식은 일부러 쓰지 않습니다. 문맥 길이에 따라 연산량이 어떻게 느는지는 소스와 공식 문서에서 확인하지 못했기 때문입니다. 대신 확인할 수 있는 것만 셉니다. 모델에 다시 넣어야 할 token 수입니다.

> 보일 셀: 6번(수업용 모델 경고)

지금부터 쓰는 것은 vLLM이 아니라 수업용 모델입니다. 산수만 하고 실제 KV 값도 GPU도 시간도 없습니다.
[예측] doc은 프롬프트 54 token에 출력 8 token입니다. KV 없이 매 step 문맥 전체를 다시 넣으면 넣는 token의 합은 얼마입니까? KV를 쓰면 얼마입니까? 힌트는 마지막에 나온 token은 다시 넣지 않는다는 것입니다.

> 보일 셀: 7번, 8번, 9번(그림)

표의 비율 칸을 위에서 아래로 읽으세요. 프롬프트가 같고 출력만 늘어난 행들과, 출력이 같고 프롬프트가 다른 행을 따로 비교합니다. 이 표는 산수이고 시간도 연산량도 아닙니다.

### 절 2. block과 KVCacheBlock (7분)

> 보일 셀: 10번

vLLM은 KV 메모리를 일정한 크기의 block으로 나눠 요청에 줍니다. 코드의 기본값은 16 token인데 이건 폴백이고 최종값이 아닙니다. 패치를 넣은 호출 기록에서 GLM-5.3-Flash는 BF16에 draft가 없을 때 TP1 4352, TP4 1152였고, 수업 구성인 TP4와 MTP 5 조합의 값은 없습니다. 서버 시작 로그로 확인한 값은 아닙니다.
가장 중요한 사실은 block이 두 세계에 나뉘어 있다는 것입니다. KVCacheBlock은 EngineCore의 Python 객체이고 ID, 참조 수, hash, 연결 포인터를 듭니다. KV 값은 GPU worker의 tensor에 있습니다. 둘은 block_id로 이어집니다. 그래서 scheduler는 GPU 메모리를 건드리지 않고 block을 나눠 주고 돌려받습니다.
첫 free block이 null block, ID 0이 되어 실제 할당 ID는 1부터입니다.

> 보일 셀: 11번, 12번, 13번, 14번

### 절 3. block table과 request의 연결 (6분)

> 보일 셀: 24번(표)

block은 pool에 있고, 어떤 요청이 어떤 block을 쓰는지는 block table에 적습니다. position 순서대로 block ID를 적은 목록입니다. 이 목록은 네 곳에 다른 모습으로 나타납니다. Request 객체는 block 목록을 들지 않습니다. group별 manager가 request ID를 키로 block 목록을 들고, SchedulerOutput이 이번 step에 알려 줄 ID를 나르고, worker가 받은 ID를 자기 block table 뒤에 붙입니다.
새 요청은 block ID 전체를, 이미 도는 요청은 새로 붙은 ID만 보냅니다. preempt에서 돌아온 요청은 예외입니다.
어느 runner를 쓰는지에 따라 worker의 클래스 이름이 다릅니다.

### 절 4. slot 공식 (8분)

계산 주체는 scheduler가 아니라 worker입니다. scheduler가 보내는 건 block ID 목록이고 slot은 없습니다.

### 절 6. 쓰기와 읽기, CUDA graph padding (5분)

> 보일 셀: 45번(쓰기와 읽기 표)

forward 안에서 KV cache는 두 번 쓰입니다. 쓰는 쪽은 slot_mapping을 보고 token마다 번호 하나로 칸에 넣습니다. 읽는 쪽은 block table과 seq_lens를 보고 요청마다 block 목록과 길이로 찾아갑니다. 쓰기와 읽기가 서로 다른 번호를 봅니다. kernel 안의 읽기 순서는 따라가지 않았으니 말하지 않겠습니다.
padding입니다. CUDA graph는 capture한 크기대로 재생하므로 실제 token 수가 적으면 capture 크기로 올립니다. 늘어난 padding token에도 slot 칸이 생기는데 값은 -1이고, 쓰기 kernel은 음수 slot을 건너뜁니다. 그래서 padding token은 KV 칸을 차지하지 않습니다. 코드 주석은 graph padding 말고 DP padding도 있다고 적습니다.

메모리 표입니다. 가상 GPU 24 GiB와 가상 모델로 계산했고, 측정이 아니라 산수입니다. 이 식은 일반 attention 층만 있는 모델의 식입니다. GLM-5.3-Flash에는 그대로 쓸 수 없습니다. TP를 늘려도 rank당 KV가 항상 비례해 줄지 않는다는 점도 기억하세요. 그리고 full 모드에서 query_start_loc을 채우는 이유는 코드 주석에 있습니다. FA3 같은 backend가 이 값이 줄어들지 않기를 요구한다는 것입니다.

### 절 1. ref_cnt: 공유와 반납 (6분)

> 보일 셀: 3번(ref_cnt 표)

두 요청의 프롬프트 앞부분이 같으면 KV도 같으니 block을 같이 쓸 수 있습니다. 그럼 한 요청이 끝났을 때 그 block을 돌려줘도 될까요. 이 판단을 정수 하나, ref_cnt가 맡습니다. 지금 이 block을 쥐고 있는 요청의 수입니다. 새로 받으면 0에서 1, prefix hit로 같이 쓰면 1 증가, 놓으면 1 감소하고 0이 된 block만 queue로 갑니다.
놓치기 쉬운 점이 둘 있습니다. ref_cnt가 0이 되어도 GPU의 KV 값은 지우지 않고, block에 붙은 hash도 지우지 않습니다. 반납은 이제 다른 요청이 가져가도 된다는 표시일 뿐입니다.

> 보일 셀: 4번, 5번, 6번

doc이 54 token을 계산한 뒤 같은 프롬프트의 faq2를 넣습니다. 표의 ref_cnt와 owners 칸을 block별로 읽고, doc과 faq2의 block table에서 같은 ID와 다른 ID를 찾으세요. hash 칸이 빈 block이 그 차이와 어떻게 이어지는지 적어 보세요.

> 보일 셀: 7번, 8번, 9번, 10번

두 요청을 차례로 끝냅니다. 반납 경로는 scheduler에서 시작해 manager와 coordinator를 거쳐 pool에서 끝납니다. doc을 반납한 행과 faq2까지 반납한 행을 비교하세요. 같이 쓰던 block은 한 요청이 놓아도 queue로 가지 않고 혼자 쥐던 block은 바로 갑니다. 마지막 행에서 cached block이 비지 않는다는 것이 반납해도 다음 요청이 적중할 수 있다는 말의 출발점입니다.
반납을 미루는 경로도 있습니다. KV connector가 block을 보내는 중일 때와, 겹쳐 도는 구성에서 connector가 consumer일 때입니다. 시뮬레이터에는 이 지연이 없습니다.

### 절 2. free queue와 eviction (7분)

> 보일 셀: 11번

ref_cnt가 0이 된 block이 놓이는 자리가 다음 재사용 순서를 정합니다. 그러니 이 자리가 곧 cache 정책입니다. free queue는 block 안의 포인터로 엮은 이중 연결 리스트입니다. 규칙은 두 줄입니다. hash가 없는 block은 앞으로 가서 먼저 재사용됩니다. hash가 있는 block은 뒤로 가서 가능한 한 늦게 재사용됩니다. 거기에 한 요청 안에서는 block을 꼬리부터 역순으로 반납합니다.
문서도 역순 반납을 적습니다. 꼬리 block은 재사용될 가능성이 낮으니 먼저 쫓겨나야 한다는 설명입니다. hash 없는 block을 앞에 두는 구분은 문서에 없고 코드와 주석이 근거입니다.
고정 예제 E3입니다. doc은 전체 62 token이고 block table은 4, 5, 6, 7이며 chat은 1, 2, 3을 계속 쥡니다. 꽉 찬 block만 hash를 얻으니 앞의 3개만 hash가 있습니다.

> 보일 셀: 18번

### 절 3. hash 사슬, salt, 적중 상한 (8분)

> 보일 셀: 24번

block을 같이 쓰려면 이 block의 KV가 내 프롬프트에도 맞는지 판단해야 합니다. KV는 그 위치까지의 token 전체에 달려 있어서 block 안 token만 비교해서는 부족합니다. 그래서 hash에 부모 block의 hash를 넣습니다. 부모, 이 block의 token, 추가 key 세 가지입니다. 같은 hash는 처음부터 이 block까지 모두 같다는 뜻이 되고, 앞 block이 하나라도 다르면 뒤 block의 hash도 전부 다릅니다.
salt는 시작 위치가 0인 block의 추가 key에만 들어가지만 부모 사슬을 타고 뒤 block 전체로 퍼집니다. 다중 사용자 환경의 격리 수단입니다. 길이 제한은 코드 안에서 갈립니다. 필드 정의는 1024자인데 실제 검증기는 128자 초과를 거부합니다. 그러니 128자 이하로 쓰세요.

> 보일 셀: 25번, 26번, 27번

doc 프롬프트의 hash 세 개를 네 조건으로 계산합니다. no_salt와 token_20_changed를 행별로 비교해 어느 행부터 갈라지는지 찾고, salt_a와 salt_b는 첫 행부터 어떤지 보세요. 54 token인데 행이 3개뿐인 이유도 적어 보세요. 시뮬레이터의 hash 값은 vLLM과 다르고 구조만 같습니다.

> 보일 셀: 28번

꽉 찬 block만 hash를 얻습니다. 그래서 앞 턴 끝의 꽉 차지 않은 마지막 block은 공유되지 않고 다음 턴이 그 1에서 15 token을 다시 계산합니다. 이 15는 기본 block 크기 16일 때의 값입니다. GLM의 큰 hybrid block에서의 값은 확인하지 않았습니다.
등록 시점은 allocate_slots 안이고, 계산이 끝날 token까지 올리되 전체 token 수를 넘지 않게 합니다. 그래서 생성한 답변의 꽉 찬 block도 다음 턴에 재사용되고, 검증되지 않은 draft token은 hash에 들어가지 않습니다.
조회 상한은 전체 token 수 빼기 1입니다. 전부 적중해도 마지막 token의 logits는 얻어야 하니 그 token은 다시 계산합니다. 적중은 block 단위라서 상한이 block 경계 바로 아래에 걸리면 block 하나가 통째로 다시 계산됩니다.

> 보일 셀: 29번(E2 예측), 30번, 31번

[예측] doc 54 token을 끝낸 뒤 네 요청을 보냅니다. 같은 프롬프트, 앞 48 token만, 20번째 token만 다른 프롬프트, 같은 프롬프트에 salt를 붙인 요청입니다. 각각의 hit token과 다시 계산할 token 수를 표로 적으세요. 특히 48 token 경우는 상한을 계산한 뒤 block 단위로 내려야 합니다.
실행 후에 max_hit_tokens와 hit_tokens를 나란히 읽고, 첫 행과 둘째 행에서 recompute가 왜 프롬프트가 짧은 쪽에서 더 큰지 설명해 보세요.

### 절 4. preempt와 recompute (5분)

> 보일 셀: 35번(단계 표)

schedule은 running 요청을 먼저 훑습니다. 줄 block이 모자라면 allocate_slots가 None을 돌려주고, 그러면 scheduler는 누군가를 내보내고 다시 시도합니다. 희생자는 선착순 정책에서 running의 마지막이고, 자기 차례가 오면 자기도 내보내고 순회를 멈춥니다. 내보내기는 block 전부 반납, 계산 수 0, draft 비움, 상태 PREEMPTED, waiting 맨 앞입니다. preempt가 있었던 step에서는 waiting을 보지 않습니다. 복귀할 때는 계산 수가 0이므로 prefix cache를 조회합니다.
이 중 희생자, 자기 자신, 복귀 세 행은 실제 Scheduler 클래스를 CPU에서 돌린 기록으로 확인됩니다. waiting을 보지 않는 행은 그 기록으로 구별되지 않아 코드 읽기로 남고, 우선순위 정책, connector 예외, speculative decoding도 코드 읽기입니다.
문서는 V1의 기본 preemption이 swap이 아니라 recompute라고 적습니다. 그 판단의 근거 PR은 찾지 못했으므로 문서의 문장까지만 말합니다.

> 보일 셀: 36번(실패 재현), 37번, 38번, 39번, 40번

pool은 usable block 11개입니다. 모자라면 schedule이 None을 받고 running의 마지막 요청이 밀려납니다. free_before가 비는 시점의 doc token이 block 경계와 어떤 관계인지 계산하고, freed ID의 순서를 2절 규칙으로 설명하세요. faq가 돌아올 때 20 token을 전부 다시 계산할까요? doc이 멈추는 길이만 바꾼 두 행이 그 답입니다. 전부 다시 계산은 항상 일어나는 일이 아니라 최악의 경우입니다. 이 표는 시뮬레이터 결과이고 실제 scheduler를 돌린 것이 아닙니다.

### 절 5. speculative decoding과 MTP (8분)

> 보일 셀: 41번

서버 구성 레시피의 값은 MTP에 draft token 5개입니다. 수업 자료에는 KV dtype이 없으므로 이 노트북은 KV dtype을 가정한 용량 숫자를 쓰지 않습니다. 이 절은 0.32.0 코드가 이렇게 적혀 있다로 읽으세요.
speculative decoding은 drafter가 K개를 먼저 제안하고 target이 한 번에 검증하는 방식입니다. 이 한 문장은 일반 설명입니다. KV 처리는 공식 문서에 설명이 없고 아래는 모두 코드 근거입니다. draft token은 Request에 붙고 전체 token 수에 포함됩니다. scheduler는 계산 수가 그 길이를 따라잡도록 줍니다. allocate_slots는 lookahead만큼 칸을 더 잡습니다. worker로는 scheduled_spec_decode_tokens에 실려 넘어갑니다. 틀린 수만큼 계산 수를 되돌립니다. 값은 지우지 않습니다.
이름이 비슷한 값이 둘 있습니다. num_lookahead_tokens는 KV 칸을 더 잡는 수이고, max_num_new_slots_for_drafting은 입력 한도에서 먼저 빼는 자리입니다. MTP와 eagle3는 lookahead가 K이고 추가 slot이 0입니다. 다른 방식 값은 표를 보세요.

> 보일 셀: 42번(E4), 43번(예측)

고정 예제 E4입니다. doc 전체 62, 계산 61에서 시작하고 K는 5입니다. 이번 step은 마지막 token 하나와 draft 다섯 개, 합 6 token을 계산합니다. 시뮬레이터는 target의 slot 쓰기만 표지로 남기고, drafter 자체의 쓰기와 맞았는지의 판정은 모델링하지 않았습니다.
[예측] 검증 결과 뽑힌 token이 3개입니다. 1개는 target이 새로 뽑았고 나머지는 받아들인 draft입니다. 받아들인 수, 거부한 수, 검증 뒤의 num_computed_tokens와 num_tokens를 계산하세요. block table은 바뀔까요?

> 보일 셀: 44번, 45번, 46번, 47번, 48번, 49번

실행 후에 무엇이 줄고 무엇이 늘고 무엇이 그대로인지 적게 합니다. 코드의 식은 세 줄입니다. 표의 칸은 KV 값이 아니라 어느 token을 계산해 썼는지 남긴 표지입니다. 끝까지 draft로 남는 행을 찾아 보세요.

> 보일 셀: 50번

되감기의 실체는 정수 하나를 줄이는 일입니다. block을 돌려주지 않고 slot을 지우지 않습니다. 읽기는 seq_lens까지만 보니 범위 밖의 옛 값을 읽을 경로가 없고, 계산이 진행되면 그 자리도 덮어쓰입니다. 이 연결은 수업의 해석입니다. 되감기에는 조건이 있습니다. preempt로 이미 무효가 된 결과에는 거부 수를 적용하지 않습니다.
틀린 KV를 지우지 않는 이유는 코드 주석이 두 가지로 적습니다. 몇 token이 거부됐는지 CPU가 모르는 채로 CPU와 GPU의 동기화를 피하려는 것, 그리고 target의 query_start_loc과 seq_lens를 그대로 재사용하려는 것입니다. 자리를 미리 잡아야 하는 이유는 버그 사례가 보여 줍니다. 새 요청의 첫 step에 lookahead block이 없어서 drafter의 KV가 prefix로 공유되는 block에 기록되어 오염된 PR 사례입니다.

### 절 6. hybrid KV와 GLM-5.3-Flash (6분)

> 보일 셀: 51번

지금까지는 모든 층이 같은 규칙을 쓴다고 가정했습니다. 층 종류가 섞이면 필요한 칸 수와 놓아도 되는 칸이 층 종류마다 달라집니다. 층마다 자기 KV spec을 밝히고, 엔진 코어가 모아서 group으로 나눕니다. 층들의 spec이 전부 한 가지면 group도 하나로 끝납니다. spec 종류는 열 개이고, 종류마다 manager가 따로 있지만 전부 같은 부모 클래스를 상속합니다.
group마다 메모리를 따로 잡지 않습니다. 같은 byte 영역을 여러 group의 층이 겹쳐 쓰고, block ID 하나는 한 번에 한 group만 소유하므로 충돌하지 않는다고 docstring이 적습니다. group이 여럿이면 적중 길이도 합의해야 합니다. 어떤 token 범위를 건너뛰려면 모든 group이 그 범위를 갖고 있어야 하기 때문입니다.

> 보일 셀: 52번, 53번, 54번, 55번, 56번

장난감 pool입니다. 층 수나 압축 같은 값은 없고 block 소유 규칙만 보여 줍니다. 어느 group이 문맥을 따라 늘고 어느 group이 처음 한 번만 받는지 읽으세요. 적중 합의 셀에서는 round마다 길이를 줄인 group이 어디인지 보세요. 세 group의 경계는 수업이 정한 값입니다.

> 보일 셀: 57번(GLM 층 표와 group 수 표)

GLM-5.3-Flash는 왜 hybrid가 필요한가. 층의 KV 규칙이 네 가지입니다. KDA 선형 층은 문맥 길이와 무관한 요청당 고정 state입니다. sparse MLA 층은 문맥에 비례합니다. MLA에 붙은 indexer cache는 비례하되 token당이 아니라 4 token에 하나입니다. tail cache는 요청당 고정 크기의 링이고 prefix caching 대상이 아닙니다.
체크포인트 값은 45층 중 선형 층이 34개, sparse 층이 11개입니다. 이 값들이 KV 크기로 이어지는 계산은 02c가 합니다.
group 수는 실제 층 클래스와 실제 group 함수를 CPU에서 불러 얻은 값입니다. GPU 서버가 아닙니다. BF16에서는 6개이고 저장 형식에 따라 5개나 7개가 됩니다. spec 종류가 넷이어도 group은 넷이 아닙니다. 왜 그 수가 되는지는 분해해 확인하지 못했습니다.
그래서 용량식 2 곱하기 B 곱하기 L 곱하기 T 곱하기 n 곱하기 d 곱하기 b는 이 모델에 그대로 쓸 수 없습니다. KDA 층에는 T가 없고, MLA 층에는 2가 없고, indexer와 tail이 더 붙고, group마다 block 크기가 다릅니다. 이 모델에서 prefix caching이 실제로 켜진 채로 뜨는지는 미확인입니다. 서버를 띄워 확인할 항목으로 남아 있습니다.

> 보일 셀: 57번 아래 표(문서와 코드가 다를 때)

문서는 coordinator가 정확히 두 group을 다룬다고 적지만, 코드는 group이 둘 이상이면 같은 coordinator를 고르고 반복 루프에 개수 제한이 없습니다. 코드가 맞고 문서는 개념 소개로만 읽으세요. 이 hybrid 구조의 대가를 기록한 RFC 둘은 2026년 11월 1일 기준 열려 있고, GLM의 측정이 아닙니다.
