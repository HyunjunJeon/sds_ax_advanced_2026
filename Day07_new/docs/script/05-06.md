# 강의 대본: 노트북 05, 06

이 대본은 강사가 소리 내어 말할 문장입니다. 가정이 두 가지 있습니다. 첫째, 한국어로 분당 300자를 말한다고 가정했고, 각 절의 말하는 글자 수는 시간표 분 x 300 x 0.8 이하로 맞췄습니다. 나머지 20%는 출력 셀을 보여 주고 질문을 받는 시간입니다. 둘째, 이 대본은 아직 아무도 소리 내어 연습해 보지 않았습니다. 실제 속도는 첫 수업에서 재 보고 고쳐야 합니다.

`> 보일 셀` 줄은 말이 아니라 화면에 띄울 셀을 가리키며 글자 수에 세지 않았습니다. 셀 번호는 현재 노트북의 0부터 세는 번호입니다. 예측 문제는 셀을 보여 주기 전에 종이에 답을 적게 하고, 답은 셀을 보인 뒤에 말합니다.

## 05-Agent-Integration

### 절 0. Part 4와 04b에서 넘어온 것 (3분)

> 보일 셀: 1번, 2번(설치된 버전 출력)

오늘은 에이전트가 서버에게 어떻게 보이는지 봅니다. 먼저 약속 하나. 이 노트북의 경로 설명은 vLLM 0.32.0의 Python frontend 기준입니다. 수업 Pod는 더 이른 빌드이고, 어떤 frontend로 떴는지 어떤 플래그로 떴는지 기록이 없습니다. 그래서 오늘 제 말은 소스에 이렇게 적혀 있다, 또는 클래스를 불러 보니 이렇게 나왔다는 뜻입니다. 수업 서버가 이렇게 돈다는 뜻이 아닙니다.
Part 4의 연결을 한 줄로 잡겠습니다. 메모리 선택으로 block이 많아지면 prefix가 cache에 오래 남고, 모자라면 앞 턴 block이 먼저 밀려납니다. 그 prefix를 GPU 밖에서 지키는 법이 바로 앞의 04b였습니다.
Part 2에서 가져올 것은 한 문장입니다. block의 hash는 앞 block의 hash, 이 block의 token, 추가 key로 만들어집니다. 그래서 앞이 한 글자라도 달라지면 그 뒤는 전부 다른 block입니다. 오늘 이야기는 모두 이 문장의 변주입니다.

### 절 1. 서버가 보는 에이전트 (8분)

> 보일 셀: 3번(개념과 코드)

서버에게 멀티턴 대화는 없습니다. 턴마다 새 요청이 하나 오고, 그 요청의 messages에 지금까지의 대화가 통째로 다시 들어 있습니다. 에이전트가 도구를 한 번 부르면 서버는 요청을 두 번 받습니다. 첫 요청은 모델이 tool_calls를 내고 거기서 정상으로 끝납니다. 두 번째는 앞 대화 뒤에 도구 결과를 붙인 새 요청입니다. 다만 응답이 length로 잘려 끝났다면 정상 종료가 아니라서 이 흐름의 예외입니다.
세션 필드는 어떨까요. session_id라는 선택 필드가 있기는 합니다. 하지만 코드를 읽으면 이 값은 KV 이벤트 메타데이터로만 흘러가고, block hash의 입력에는 들어가지 않습니다. 그러니 vLLM에 세션이 전혀 없다가 아니라, 세션 필드는 있지만 재사용과는 상관이 없다가 정확합니다. 이건 코드 읽기입니다. 공식 문서에는 멀티턴이 턴마다 새 요청이라는 설명이 없어서 소스로 확인했습니다.

> 보일 셀: 4번(요청 열 표)

손으로 쓴 예시 대화입니다. 요청이 세 번 나가는데, 앞 요청과 같은 앞부분 메시지 칸을 보세요. 요청마다 앞부분은 그대로고 끝에만 메시지가 붙습니다. toy token 수는 요청마다 늘어납니다. 서버가 새로 계산할 양이 이 늘어난 총량이 아니라 붙은 만큼이면 이상적입니다.

> 보일 셀: 6번(hash 입력 표)

그렇게 되려면 앞 요청의 KV가 남아 있어야 하고, 열쇠는 hash 입력입니다. 앞 block의 hash, 이 block의 token은 들어갑니다. LoRA와 멀티모달 같은 추가 key도 해당하면 들어갑니다. cache_salt는 시작 위치가 0인 block에만 들어갑니다. session_id는 들어가지 않습니다.
이 설계의 이유는 수업의 해석입니다. 재사용을 세션이 아니라 prefix hash에 맡기면 서버가 대화를 기억할 필요가 없습니다. 같은 앞부분이면 누가 보냈든 같은 block을 씁니다. 그러면 질문은 하나로 모입니다. 클라이언트가 앞 대화를 얼마나 똑같이 다시 보내느냐. 다음 두 절이 그 이야기입니다.

### 절 2. prefix 재사용과 깨지는 조건 (11분)

> 보일 셀: 7번(수업용 모델 경고)

가장 먼저 경고합니다. 이 절의 표는 vLLM이 아니라 수업용 모델입니다. 단어 단위 toy token에, 재사용 판정만 block hash 규칙을 옮긴 모델에 맡겼습니다. 진짜 GLM의 tokenizer도 chat template도 쓰지 않았고, 시간 값은 만들지 않았습니다. 숫자는 vLLM이 이렇게 했다가 아니라 규칙을 이렇게 옮기면 이렇게 나온다입니다.
코드 쪽 사실은 이렇습니다. prefix caching은 기본으로 켜져 있고 해시 알고리즘 기본값은 sha256입니다. 공식 문서는 켜는 방법만 적고 기본값은 적지 않습니다. 코드가 강제로 끄는 구성도 있습니다. 그리고 GLM 서버가 켜진 채로 뜨는지는 실행으로 확인하지 못했습니다.

> 보일 셀: 7번 끝의 예측 문단

[예측] append_only에서 세 번째 턴의 hit_ratio는 0.5 아래, 0.5에서 0.8 사이, 0.8 위 중 어디일까요. 새로 붙은 부분의 비율로 이유를 한 줄 적으세요.

> 보일 셀: 8번, 9번(append_only)

덧붙이기만 하는 기본 시나리오입니다. 첫 턴은 적중 0이고, 이후 턴은 앞 턴의 꽉 찬 block만큼 적중합니다. recomputed_tokens가 사용자 입력과 답변 길이 정도에 머무는 것도 보세요.

> 보일 셀: 11번(예측)

[예측] 3번째 턴부터 system prompt의 맨 앞 문장만 바꿉니다. 3번째 턴의 적중 token은 얼마일까요. 4번째 턴은 회복될까요. 종이에 적으세요.

> 보일 셀: 12번, 13번(system_change)

변경 턴의 적중은 0입니다. 다음 턴이 다시 적중하는 건 4번째 요청이 새 system prompt를 가진 3번째 요청의 block을 재사용하기 때문입니다. 깨진 건 한 번뿐이고 새 prefix가 자리를 잡습니다. 이것이 사슬 hash의 값입니다. 앞이 같으면 뒤를 믿고, 앞이 다르면 뒤를 못 믿습니다.

> 보일 셀: 14번, 15번(tool 목록)

tool 목록을 바꾸는 시나리오입니다. 이 표에서 변경 턴의 적중이 부분적으로 남는 건 toy가 tools를 system 뒤에 둔다고 가정했기 때문입니다. 실제 GLM 체크포인트의 chat template은 tool 정의를 system보다 앞에 렌더링합니다. 이 판단은 revision 46a050b의 template을 진짜 tokenizer로 렌더링해 비교한 구성 문자열 결과이고, 서버를 돌린 결과가 아닙니다. 수업 Pod가 같은 revision인지는 모릅니다. 208 token짜리 대화에서 첫 차이는 tool 순서를 바꾸면 50번째, 하나를 빼면 88번째, system 문구를 바꾸면 193번째 token이었습니다. 서버가 tool 순서를 정렬해 주지도 않습니다. 수업의 권장은 대화 도중에 tool을 바꾸지 말고 순서도 고정하는 것입니다.

> 보일 셀: 16번, 17번(effort)

effort도 비슷합니다. template은 effort 줄을 prompt 맨 앞에 넣습니다. 같은 비교에서 low, high, max는 8번째 token에서 갈라졌고, 이건 첫 block 안입니다. medium은 max와 같은 문자열이었습니다. 그러니 effort를 바꾸면 이전 값으로 쌓은 block을 하나도 못 씁니다. 역시 서버 cached_tokens 측정이 아닙니다.

> 보일 셀: 18번, 19번(pressure_evict)

filler가 끼어드는 시나리오입니다. 블록 수를 일부러 줄여 효과를 크게 보여 줍니다. 앞 턴 block이 다른 요청 때문에 밀려나고, 밀려난 block의 뒤는 사슬이 끊겨 함께 쓸모를 잃습니다. 실제 서버에서 얼마나 자주 나는지는 이 표로 알 수 없습니다.

> 보일 셀: 20번, 21번(조회 상한)

똑같은 요청을 두 번 보내도 한 block이 다시 계산됩니다. 마지막 token의 logits이 필요해서 최소 한 token은 다시 계산해야 하고, 조회 상한이 token 수 빼기 1이기 때문입니다. 소스 주석이 이유를 직접 말합니다. 반면 꽉 차지 않은 마지막 block은 다른 이유로 다시 계산합니다. hash가 꽉 찬 block에만 만들어지기 때문이고, 그래서 다음 턴이 앞 턴 끝에서 다시 계산하는 건 마지막 1에서 15 token이고, 이 최대 15는 조회 상한이 아니라 이 tail에서 나온 값입니다.

> 보일 셀: 22번

확정 행과 미확인 행을 구분해 읽으세요. 부분 tail, 조회 상한, 어긋난 token, system 변경, eviction은 확정입니다. 답변이 다시 tokenize될 때의 어긋남은 미확인이라 사실로 말하지 않습니다. tool 목록과 effort는 template 구성 문자열 비교로 일치했습니다.

### 절 3. create_deep_agent가 매 턴 보내는 것 (12분)

> 보일 셀: 24번, 25번(기록용 모델 정의)

프레임워크는 대화 상태를 대신 관리해서, 서버로 나가는 요청을 직접 볼 일이 드뭅니다. 그런데 서버의 재사용은 프레임워크가 매 턴 같은 앞부분을 만들어 주느냐에 달려 있습니다. 네트워크 없이 그 앞부분을 봅시다. RecordingChatModel은 모델 객체가 받는 입력을 기록합니다. 서버로 나가는 요청 본문이 아니므로 둘이 같다고는 말하지 않습니다. 주의 하나. pydantic이 list를 복사하니 기록은 model.calls에서 읽어야 합니다.

> 보일 셀: 26번(예측)

[예측] 스크립트는 도구 호출 둘과 최종 답변 하나입니다. 모델은 몇 번 불릴까요. 두 번째 호출의 messages는 첫 호출과 어떤 관계일까요. 호출 횟수와 tools 개수를 적으세요.

> 보일 셀: 27번, 28번, 29번

모델은 세 번 불렸습니다. 기본 구성에서 system 글자 수는 0이고, 도구는 여덟 개입니다. 도구 사용 안내문은 따로 넣지 않고 스키마 설명에 맡깁니다. 호출이 늘 때마다 assistant와 tool이 하나씩 붙습니다. tool call을 낸 요청은 거기서 끝나고 다음 요청은 결과를 붙인 새 요청입니다.

> 보일 셀: 30번, 31번

세 호출에서 system과 tools의 sha256이 같고, 앞 호출의 messages로 시작하는지도 모두 참입니다. 이 기본 구성에서는 system과 tools가 바이트 단위로 안정적이고 messages는 덧붙기만 합니다. 서버 재사용에 유리한 모양입니다. 단, 이 호출 열에 대한 확인일 뿐입니다. 긴 실행에서는 앞쪽 messages가 바뀝니다. 가짜 서버로 2000자가 넘는 write_file 인자를 쓰게 했더니, 24개 messages인 요청부터 앞쪽 assistant 메시지의 인자가 줄어 앞부분이 달라졌습니다. 요약이 실제로 발동하는 경우와 skills, memory 내용이 바뀌는 경우는 실행하지 않았습니다.

> 보일 셀: 31번 아래 예측 문단

[예측] 이 기록을 toy 렌더러에 넣으면 두 번째 호출의 hit_ratio는 높을까요, 낮을까요. 도구 8개를 떠올리고 답하세요.

> 보일 셀: 32번, 33번

높습니다. 도구 스키마가 길어 앞부분이 크고 그 뒤에 메시지 몇 개가 붙을 뿐이기 때문입니다. 마지막 칸이 이 결과는 toy 가정 위에 있다고 알립니다. 실제 template은 tools가 system보다 앞입니다.
이어서 reasoning을 되돌려 보내지 않을 때입니다. ChatOpenAI는 다음 턴에 assistant 메시지에 reasoning을 다시 싣지 않았습니다. 그러면 template은 그 자리를 빈 think 태그로 렌더링합니다. 구성 문자열 비교에서 다음 턴은 앞 턴 prompt가 끝나는 166번째 token에서 갈라졌습니다. 그래서 재사용은 앞 턴 prompt 안의 꽉 찬 block까지, 앞 턴 답변 구간은 다시 계산합니다. openai SDK로 reasoning을 다시 보내면 clear_thinking이 거짓일 때 188번째까지 일치하고, 참이면 다시 166번째에서 갈라집니다. 서버 측정이 아닙니다.
마지막으로 task.md와 잇습니다. 수업의 권장 순서는 이렇습니다. 에이전트를 만든 뒤 해시가 호출 사이에 같은지 보고, 시각이나 요청 번호를 system 앞쪽에 넣지 말고, 도구를 도중에 바꾸지 마세요. deepagents의 prompt caching middleware는 Anthropic 같은 모델용이고, 서버의 prefix cache와는 별개입니다.

### 절 4. cached_tokens와 usage (8분)

> 보일 셀: 34번

재사용이 일어나는지는 응답의 usage 아래 cached_tokens로 봅니다. 이 값이 실리는 조건은 서버 플래그 하나에, 스트리밍일 때의 조건 둘이 더해진 셋입니다. 첫째, 서버에 enable-prompt-tokens-details 플래그가 있어야 합니다. 기본이 False라서 없으면 null입니다. 공식 문서에서 이 플래그 설명은 찾지 못했고 코드가 유일한 근거입니다. 둘째, 스트리밍이면 요청에 include_usage가 실려야 합니다. 서버가 강제로 켤 수도 있습니다. 셋째, ChatOpenAI에 base_url을 주면 stream_usage가 켜지지 않으니 True를 직접 줘야 합니다. 수업 Pod가 이 플래그를 켰는지는 기록이 없습니다.

> 보일 셀: 35번, 36번

서버 플래그 칸이 False면 다른 칸이 아무리 좋아도 전부 False입니다. 이 표는 규칙을 옮긴 판정 함수의 출력이고 서버에서 확인한 값이 아닙니다.

> 보일 셀: 37번, 38번

실패 재현입니다. 서버 플래그를 켠 서버에 스트리밍이어도 기본값 클라이언트는 False로 끝납니다. 예외는 나지 않습니다. 오류가 없다는 점이 이 실패의 성격입니다. 그래서 null이면 서버 플래그, 스트리밍 여부와 include_usage, 마지막으로 클라이언트 stream_usage 순으로 확인하세요.

> 보일 셀: 39번, 40번

가짜 서버에 ChatOpenAI를 연결해 실제로 나가는 요청 본문을 봤습니다. stream_options 칸과 input_token_details 칸이 짝으로 움직입니다. 이 가짜 서버는 이 노트북 안에서 정의한 것이고 vLLM이 아닙니다.

### 절 5. cache_salt (5분)

> 보일 셀: 41번

prefix cache는 같은 앞부분이면 누구에게든 재사용을 허용합니다. 서로 모르는 사용자가 한 서버를 쓰면 이게 정보 노출 경로가 될 수 있습니다. cache_salt는 값이 다르면 서로의 block을 쓰지 못하게 합니다. 문서의 보안 절이 격리를 목적으로 밝힙니다. 코드로는 시작 위치 0인 block의 추가 key에만 들어가고, 첫 block이 달라지면 뒤도 모두 달라지므로 다른 salt는 어떤 block도 공유하지 못합니다. 비용도 있습니다. 사용자마다 다른 salt면 같은 system prompt의 재사용도 사라집니다.

> 보일 셀: 42번, 43번

salt가 user-a에서 user-b로 바뀐 턴의 적중을 보세요. 대화 앞부분이 같은데 0입니다. 공통 prompt 재사용을 포기하는 비용의 크기입니다. 사용자 격리가 필요 없는 환경이라면 salt를 안 주는 쪽이 유리합니다.

> 보일 셀: 44번, 45번

길이 제한은 코드 안에서 둘로 갈립니다. 필드 정의는 1024지만 검증기는 128자를 넘거나 골뱅이, 슬래시, 역슬래시, NUL이 있으면 거부합니다. 128자는 통과하고 129자는 거절됩니다. 문서와 블로그는 이 제한을 적지 않으니, 128자 이하로 안내하세요.

### 절 6. reasoning 필드와 effort (6분)

> 보일 셀: 46번

사고 과정을 내는 모델은 사고와 최종 답을 따로 담습니다. v0.32.0의 응답에서 필드 이름은 reasoning 하나입니다. 옛 이름 reasoning_content는 응답에서 사라졌고, 요청 쪽에서만 바꿔 받아 줍니다. 공식 문서가 이름이 바뀌었으니 클라이언트도 고치라고 경고합니다. 수업 Pod가 어느 이름을 쓰는지는 응답으로 확인해야 합니다.
ChatOpenAI가 사고 과정을 안 보여 주는 건 버그가 아니라 설계입니다. 모듈 문서가 공식 규격 필드만 읽고 제3자 비표준 필드는 보존하지 않는다고 직접 말합니다.

> 보일 셀: 47번, 48번

additional_kwargs의 키에 reasoning이 없습니다. 스트리밍도 같습니다. 같은 모양의 JSON을 손으로 읽는 함수는 두 이름 모두 읽습니다. 사고가 먼저 스트리밍되면 첫 chunk가 reasoning일 수 있어서, 엔진의 첫 token 시간과 사용자가 처음 보는 답변은 다른 시점입니다.

> 보일 셀: 48번 아래 effort 설명, 49번, 50번

effort는 두 길로 보낼 수 있습니다. extra_body의 chat_template_kwargs로 보내거나 최상위 필드로 보냅니다. 서버는 template이 선언한 변수, tokenizer의 이름 있는 인자, HF 기본 인자만 통과시키고, 최상위 값이 오면 그쪽이 덮어씁니다. 최상위 경로의 허용값이 vLLM과 호환되는지는 실측하지 않았습니다.
캐시와의 관계는 절 2에서 말한 대로입니다. 이 과정의 두 스크립트는 하나는 max, 하나는 low를 보내므로 같은 서버에 섞어 쓰면 서로의 prefix를 못 씁니다. clear_thinking은 vLLM 옵션이 아니라 template이 선언한 변수이고, 두 스크립트는 user 메시지 하나만 보내서 이 값이 prompt를 바꾸지 않습니다. 다만 Pod의 template이 같은 변수를 읽는지는 미확인입니다.

## 06-Tool-Calling-Errors

### 절 0. 여섯 층 지도 (5분)

> 보일 셀: 0번(학습 목표), 1번(층 표)

서버가 200 OK를 주는데 tool_calls가 비어 있다. 인자가 이상하다. 같은 요청이 스트리밍에서만 다르게 끝난다. 이걸 모델이 이상하다로 뭉뚱그리지 말고 어느 층에서 생겼는지 찾는 것이 오늘의 연습입니다.
층은 여섯입니다. chat template, 생성, parser, schema 검증, 실행, 네트워크. 이 여섯 층은 vLLM의 설계가 아니라 수업이 진단을 위해 나눈 구분입니다. 증상이 같아도 층이 다르면 고치는 곳이 다르기 때문입니다. parser 층은 API server 프로세스에서 detokenize가 끝난 text에 적용됩니다. schema 검증은 서버가 하지 않는 것으로 읽히고 client 몫입니다.

> 보일 셀: 1번 아래 이 노트북이 말하는 방식

근거 종류를 먼저 외워 둡시다. 첫째, 실제 GLM 파서에 사람이 만든 문자열을 넣은 구성 문자열 결과. 둘째, 실제 tokenizer와 serving 제너레이터까지 돌린 실제 클래스 실행. 셋째, xgrammar 입력 시험. 넷째, Rust 파서 crate만 돌린 결과. 다섯째, 소스를 읽은 코드 읽기. 어느 것도 GPU 서버나 수업 Pod에서 관찰한 것이 아닙니다. 그래서 실패 사례 후보 C1부터 C12는 이 노트북 어디서도 관찰됐다고 쓰지 않습니다.

> 보일 셀: 3번, 4번(차선 그림)

그림에서 validate args와 run tool은 client 줄에 있습니다. vLLM 서버 안에는 이 두 상자가 없습니다. 서버가 200을 줬다는 건 parser 층까지 통과했다는 뜻이지 인자가 맞다는 뜻이 아닙니다.

### 절 1. 세 플래그의 조합 (7분)

> 보일 셀: 5번

레시피는 도구 호출에 tool-call-parser, enable-auto-tool-choice, reasoning-parser 세 플래그를 함께 주라고 합니다. 앞의 둘은 이름이 비슷하지만 역할이 다릅니다. 하나는 어떤 파서 클래스를 쓸지 고르는 값, 하나는 모델이 스스로 도구를 고르는 auto 모드의 스위치입니다. 공식 문서는 둘이 모두 필요하다고 하고, 한쪽만 줬을 때의 결과는 적지 않습니다. 코드를 읽으면 세 곳이 보입니다. auto 스위치만 있고 파서 이름이 없으면 TypeError로 서버가 뜨지 않습니다. 반대로 스위치가 꺼져 있으면 파서를 풀지 않습니다. 그리고 두 플래그 없는 서버에 tools를 보내면, tool_choice를 생략해도 auto로 채워져 렌더링 단계에서 오류 응답이 만들어집니다. none은 통과합니다. 기본 오류 상태가 400이라는 것도 코드 읽기이고, 응답 본문을 받아 본 사람은 없습니다.

> 보일 셀: 6번(예측)

[예측] 파서 플래그만 주고 auto 플래그를 안 준 서버는 시작에 실패할까요, 성공할까요. 성공한다면 tools를 보냈을 때 어느 단계에서 어떻게 보일까요. 한 줄로 적으세요.

> 보일 셀: 7번, 8번, 9번

네 조합 중 시작 실패는 한 행뿐입니다. 나머지 셋은 정상으로 뜹니다. 파서 플래그만 주면 시작 오류는 없지만, tools를 보내는 첫 요청에서 400이 납니다. tools가 없는 요청은 정상이라 상태 점검만으로는 안 드러납니다. 이것이 진단의 함정입니다. 네 행 모두 코드 읽기이고 네 조합을 실제로 띄운 기록은 이 수업에 없습니다. 수업 Pod가 이 플래그로 떴는지도 미확인이라, tools를 보내 tool_calls가 실제로 오는지로 확인하세요.

### 절 2. 파서의 구조 (7분)

> 보일 셀: 10번

GLM 도구 호출은 tool_call 태그 안에 함수명, arg_key, arg_value가 이어지는 XML 비슷한 마크업입니다. 모델은 JSON을 쓰지 않습니다. 인자 JSON은 파서가 만듭니다. 이 문장을 기억해 두세요. 뒤의 잘림 이야기가 전부 여기서 나옵니다.
문서는 glm45는 4.5와 4.6용, glm47은 4.7용으로 나눠 안내합니다. 그런데 Python 서버에서는 두 이름이 같은 클래스를 가리킵니다. reasoning 파서도 마찬가지입니다. 도구 파서 파일은 14줄이고 세 값만 정합니다. 파싱 로직은 없습니다. 실제 파싱은 ParserEngine 위에 만든 Glm47MoeParser가 합니다. 그러니 동작을 확인하려면 껍질 파일이 아니라 파서 본체와 엔진 파일을 읽어야 합니다. 이름이 구현을 가르는 곳은 Rust frontend이고, 절 7에서 봅니다.

> 보일 셀: 11번

표로 보면 네 설정 이름이 둘로 모입니다. 근거는 코드 읽기입니다.
엔진 기반 파서는 요청의 skip_special_tokens를 거짓으로 바꿉니다. GLM tokenizer에서 마크업은 all_special_tokens에 들지 않아 이 값과 상관없이 남습니다. 지워지는 건 observation 같은 특수 token입니다. 이건 실제 tokenizer로 확인했습니다.
서빙 쪽에서는 비스트리밍이 parse를, 스트리밍이 조각마다 parse_delta를 부릅니다.

> 보일 셀: 12번

마크업을 문자열로 조립만 해 본 셀입니다. 파서를 돌린 게 아니고 모델 출력도 아닙니다. 조립 규칙을 손으로 옮겼을 뿐입니다.

### 절 3. 구성 문자열로 본 파서 결과 (11분)

ran 기록이 없으면 결과를 지어내지 않고 멈추는 약속이 있습니다. 이 약속이 있어야 근거 종류 칸을 믿을 수 있습니다.

이제 잘림입니다. max_tokens로 호출 중간에 끊기면 어디서 끊겼는지에 따라 모양이 네 가지로 갈립니다. 코드는 출력이 끝나면 열린 호출을 닫는 이벤트를 억지로 넣고, 이름이 선언된 도구인지 확인하고, 닫힌 쌍으로 인자를 만듭니다. 비스트리밍에서는 닫히지 않은 마지막 쌍이 정규식에 걸리지 않아 사라집니다. 스트리밍은 값을 먼저 내보내므로 사정이 다릅니다. 표의 네 위치는 실제 파서와 제너레이터에 넣은 결과입니다.

> 보일 셀: 25번, 26번

선언하지 않은 이름의 호출이 사라지고 content도 비는 것은 이 구성 문자열에서의 사실이고, 스트리밍과 비스트리밍이 같습니다. 클라이언트에서 보이는 증상은 tool_calls가 비었는데 completion_tokens는 크다입니다. 원문을 보려면 요청에 return_token_ids를 실어 응답의 token_ids를 decode합니다. 서버 출력 로그는 두 플래그를 함께 켜야 남고, 비스트리밍 요청은 이 경우 아무것도 남기지 않습니다. 둘 다 코드 읽기이고 실행하지 않았습니다. 다만 기본 구조화 태그의 문법은 이 이름을 거절합니다. 엔진 집행은 돌리지 않았으니, 이 증상은 태그가 없는 서버의 이야기로 읽습니다. tools가 빈 목록인 요청은 파서까지 오지 않고 요청 검증에서 거절됩니다.

> 보일 셀: 27번, 28번

파서가 낸 인자를 믿을 수 있을까요. 서버가 필수 인자나 타입을 검증한다는 코드는 읽은 범위에서 찾지 못했습니다. 단정은 아닙니다. 아래 검증 함수는 vLLM 기능이 아니라 수업이 만든 client 쪽 검증입니다. 잘린 호출은 필수 인자 누락으로, 타입 불일치는 타입 오류로 걸립니다.

> 보일 셀: 29번, 30번

검증 없이 실행하면 한 도구는 예외로 죽고, 다른 도구는 예외 없이 곧이라는 글자를 수십 번 반복한 문자열을 만듭니다. 예외 없는 실패가 더 위험합니다. 스트리밍으로 모은 인자는 json.loads에서 실패하고, 비스트리밍은 올바른 JSON입니다. 검증 메시지를 모델에게 돌려주는 것이 복구 경로입니다.

### 절 4. tool_choice와 strict 수준 (8분)

> 보일 셀: 31번

tool_choice는 네 값입니다. auto는 모델이 고르고, required는 한 번 이상, 이름 지정은 그 함수 하나, none은 호출하지 않습니다. 별개로 도구마다 strict 필드가 있고, 서버에 하한 플래그가 있습니다. 공식 문서는 required와 이름 지정이 JSON 스키마 구조화 출력을 쓴다고 설명합니다. 그런데 GLM에서는 일부가 맞지 않습니다.
GLM 도구 파서는 required와 이름 지정에 JSON 스키마 강제를 걸지 않습니다. 둘 다 auto와 같은 XML 파싱 경로를 탑니다. 대신 환경변수가 참이면 구조화 태그가 붙습니다. 호출이 한 번 이상 나오게 짜고, 이름 지정은 첫 호출 뒤에 멈추게 더합니다. 이 태그는 엔진의 grammar 마스크로 집행되므로 temperature와 무관하다는 건 코드 읽기입니다.
none은 마크업을 지나가며 호출 이벤트를 억제할 뿐 문법이 막는 건 아닙니다. 기본값에서는 도구 정의가 프롬프트에 그대로 남습니다.

> 보일 셀: 32번

문서와 코드가 다른 네 곳입니다. 코드가 맞습니다. 네 행 모두 코드 읽기이고 서버로 확인하지 않았습니다.

> 보일 셀: 33번, 34번

auto는 파서 기본 수준이 FUNCTION이라 strict가 없어도 마크업과 함수명 껍데기가 제약됩니다. 인자 스키마 전체를 고정하는 길은 strict 도구이거나 parameter 수준뿐입니다. 환경변수를 거짓으로 하면 구조화 태그를 붙이지 않아 GLM의 required와 이름 지정에는 제약이 남지 않습니다.

> 보일 셀: 35번, 36번

기본 태그를 xgrammar로 컴파일해 token을 대 본 표입니다. 엔진이 sampling 마스크로 집행한 결과가 아닙니다. 문법 통과가 거짓인 행을 찾으세요. 중복 시작 태그, 선언하지 않은 이름, 타입이 틀린 값에서 거절됐습니다. 잘린 문자열이 통과한 건 문법을 어기기 전에 끊겼기 때문입니다. 제약이 닿지 않는 실행과 의미 층은 그대로 client 몫입니다.

### 절 5. finish_reason (6분)

> 보일 셀: 37번

finish_reason은 응답이 왜 끝났는지입니다. 이 규칙을 설명한 공식 문서는 찾지 못했습니다. 표는 서버 코드를 옮긴 수업용 모델입니다.

> 보일 셀: 37번 아래 예측

[예측] 엔진이 length로 끝났는데 호출 하나가 추출된 상태를 auto로 두면, 비스트리밍과 스트리밍의 finish_reason은 각각 무엇일까요. required라면 어떻게 달라질까요.

> 보일 셀: 38번, 39번

auto에서 length인 두 행은 스트리밍 칸만 다른데 값이 다릅니다. 비스트리밍은 호출이 하나라도 추출되면 length여도 tool_calls로 덮어씁니다. 스트리밍은 도구 델타가 나갔고 이름 지정이 아니며 엔진 종료가 stop일 때만 tool_calls로 바꿉니다. 그래서 같은 잘림이 비스트리밍에서는 tool_calls, 스트리밍에서는 length입니다. required와 이름 지정과 none 행은 코드 읽기입니다. 정상 종료만 도구 결과를 붙인 다음 턴으로 이어지는데, 비스트리밍은 잘려도 tool_calls라서 이 값만으로 구별하지 못합니다.

> 보일 셀: 40번, 41번

실제 제너레이터 결과와 맞춰 본 표입니다. 규칙과 같음 칸이 모두 참이라 auto에서는 수업용 규칙이 제너레이터와 같습니다. truncated_call은 비스트리밍이 빈 인자와 tool_calls, 스트리밍이 닫히지 않은 JSON과 length입니다. malformed_markup은 엔진 종료가 stop이라 스트리밍도 tool_calls인데 인자가 JSON이 아닙니다. length가 아니라고 스트리밍 인자를 믿을 수는 없습니다. 이 모양은 기본 태그가 켜진 서버라면 생성되지 않아야 하니 태그 없는 서버의 이야기입니다. 이 11개 문자열 밖의 입력에서 같다는 보장은 아닙니다.
수업의 권장입니다. 도구를 실행하기 전에 completion_tokens가 max_tokens에 닿았는지, 인자가 json.loads와 검증을 통과하는지 함께 보세요.

### 절 6. reasoning 파서와의 상호작용 (4분)

### 절 7. Python 경로와 Rust 경로 (4분)

> 보일 셀: 46번

지금까지는 Python frontend였습니다. 그런데 GLM 레시피의 기본 명령은 Rust frontend를 켭니다. Rust는 스스로 실험 기능이라고 밝힙니다. 수업 Pod가 어느 frontend인지는 확인되지 않았습니다. 그래서 이 절의 어떤 문장도 수업 서버가 이렇게 동작한다로 읽으면 안 됩니다.
Rust 파서는 열린 호출이 끝에 남으면 incomplete 오류를 돌려줍니다. Python처럼 부분 인자를 살리지 않고 선언하지 않은 이름도 거르지 않습니다. 이건 파서 crate를 돌린 결과이고 tokenizer는 시험용 대체물입니다. chat 층이 그 오류를 HTTP 오류로 바꾸지 않고 text로 되돌린다는 건 코드 읽기이고 실행하지 않았습니다.

> 보일 셀: 47번, 48번, 49번

이름이 구현을 가릅니다. glm45는 이름 뒤 개행을 요구해서, 수업 형식의 clean_call이 일반 프롬프트에서 오류가 납니다. Python에서 무해한 glm45와 glm47 혼용이 Rust에서는 무해하지 않습니다. 수업의 권장은 레시피대로 glm47입니다. 미확인으로 남는 것을 읽어 보세요. 오류가 응답에서 어떤 상태 코드와 finish_reason으로 나가는지, 진짜 tokenizer와 chat 층, 수업 Pod의 frontend입니다.
