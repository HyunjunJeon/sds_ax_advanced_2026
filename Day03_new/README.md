# Day03_new — Multi-Agent System 설계 노트북 과정

Day01, Day02_new처럼 노트북을 위에서 아래로 실행하며 배우는 과정입니다. 한 교시가 노트북 하나입니다. 하루 내내 **같은 고객 요청 하나**("결제가 두 번 됐어요. 취소하고 보상안도 함께 확인해 주세요.")를 여러 구조로 처리하고, 구조 사이의 차이를 사례 차이와 섞지 않고 읽습니다. 이 폴더는 `../Day02_new/`와 별개로 돌아갑니다. 노트북과 `mas_lab/`, `rag_lab/`은 `Day02_new`를 import하지 않으며, 이 폴더의 작업이 `../Day02_new/`를 바꾸지 않습니다.

## 이 과정이 가르치는 것

Agent를 몇 개 만들지가 아니라 **어디에 판단을 맡길지**를 묻는 과정입니다. 다섯 가지를 차례로 익히고 마지막에 한 번 옮겨 봅니다.

1. Workflow와 Agent의 경계: 다음 행동을 누가 고르는지, 돈을 움직일 실행 권한이 누구에게 있는지, Single 기준선이 무엇인지
2. Agent Architecture의 변화: 구조가 직전 구조의 어떤 한계 때문에 나왔고 무엇을 새로 치르는지. Supervisor와 Handoff를 실제로 실행해 비교. 프레임워크가 자동으로 붙이는 하위 에이전트와 설계한 담당자의 차이도 모델 없이 확인
3. 네 가지 흐름: 순차·병렬·분기·루프를 `StateGraph`로 직접 만들고 각각의 실패를 재현한 뒤 패턴 이름을 네 흐름으로 번역
4. Graph Engineering(이 과정이 세우는 정의): 작업 계약, 전달 계약, 공유 예산, 실패별 다음 행동, 부분 실패, 승인과 멱등을 그래프에 넣기
5. Multi-Agent 선택 기준: Single의 실패를 먼저 분류하고 같은 조건에서 구조를 재어 선택 근거를 기록하기. Workflow와 Agent 전제, harness 일관성, 공식 프레임워크와의 대응도 확인

마지막 06은 EXA 웹 검색으로 같은 주제를 병렬·직렬·연쇄 세 구조로 리서치하는 실습입니다. 근거(Evidence)를 인용하고, 고객(entity)과 기준일(as_of)로 범위를 걸고, 예산(budget) 안에서만 일하게 하는 것이 내내 쓰는 틀입니다.

사례 자료는 모두 수업용 가상 데이터입니다. 사내 문서 11개(알파 4, 베타 1, 공통 6)와 평가 사례 12개, 결제·가용률 사실 파일 둘이 `data/`에 있습니다. 문서 검색은 BM25 하나이고 메모리 안에서 색인을 만듭니다. 별도 서버도 임베딩 모델 내려받기도 없습니다. 한국어 형태소 분석기 Kiwi는 처음 쓸 때 사전을 적재하느라 첫 호출이 느릴 수 있습니다(00에서 시간을 잽니다).

## 설치와 실행

설치는 **저장소 루트에서 한 번**, 실행은 **`Day03_new/`에서** 합니다.

```bash
# 저장소 루트에서 (한 번만)
uv sync --locked

# 이 폴더에서
cd Day03_new
uv run jupyter lab
```

- 이 폴더 안에서 `uv sync`를 실행하지 않습니다. 환경은 루트에 하나만 있고, 이 폴더에서 실행하면 다른 Day에 필요한 패키지가 지워집니다. 잘못 실행했다면 루트에서 `uv sync --locked`로 복구합니다.
- 이 폴더에는 `pyproject.toml`이 없습니다. `uv run`이 루트 환경을 찾아 씁니다.
- 작업 폴더가 `Day03_new/`여야 `import mas_lab`이 됩니다. 00의 해보기 2가 이것을 직접 확인합니다.

## API 키 설정 (필수)

이 과정은 실제 모델과 실제 웹 검색만 씁니다. **키가 없으면 노트북은 키를 확인하는 셀에서 한국어 안내와 함께 멈춥니다.** 키 없이 도는 경로는 없습니다. 키는 두 개이고 둘 다 필요합니다.

| 키 | 쓰는 곳 | 발급 | 비용을 내는 주체 |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | 모든 노트북의 모델 호출 | Anthropic 콘솔 | 내 Anthropic 크레딧 |
| `EXA_API_KEY` | 00의 확인 셀과 06의 필수 리서치 실습 | `https://exa.ai/` (구글 로그인을 추천합니다) | 내 EXA 크레딧 |

- 제공자는 Anthropic이고 `ChatAnthropic`으로 부릅니다. 기본 모델은 `claude-sonnet-5-5`, 기본 추론 깊이(effort)는 `medium`입니다(`.env.example`의 `DAY02_MODEL`, `DAY02_EFFORT`). 변수 이름이 `DAY02_`로 시작하는 것은 `Day02_new/.env`를 고치지 않고 복사해 쓰게 하려는 것입니다.
- 01~05는 `ANTHROPIC_API_KEY`만 씁니다. 그래도 00의 키 확인 셀이 두 키를 모두 요구하므로 00을 통과하려면 둘 다 채워야 합니다.

방법은 둘 중 하나를 고릅니다. 어느 쪽이든 키 값은 **본인이 직접** 채웁니다.

```bash
# 방법 1: 양식을 복사해 두 키를 직접 입력 (Day03_new/ 안에서)
cp .env.example .env

# 방법 2: Day02_new/.env가 이미 있다면 복사한 뒤 EXA_API_KEY만 더하기
cp ../Day02_new/.env .env
```

방법 2에서는 `ANTHROPIC_API_KEY`와 모델 이름이 그대로 들어 있습니다. `Day02_new/.env`에는 EXA 항목이 없으므로, 편집기로 복사한 `.env`를 열어 `EXA_API_KEY=` 줄을 새로 더하고 그 뒤에 EXA 키를 직접 넣습니다.

- 키는 이 폴더의 `.env`에서만 읽습니다. 셸에 export한 키나 다른 Day의 `.env`는 읽지 않습니다. 모르는 사이에 내가 아닌 계정의 크레딧이 쓰이는 사고를 막기 위해서입니다.
- `.env`를 고친 뒤에는 **kernel을 재시작**해야 반영됩니다.
- `.env`는 커밋하지 않습니다(`.gitignore`). 값을 노트북 출력이나 채팅에 붙여 넣지 않습니다. 도구가 보여 주는 것은 `설정됨`과 `미설정`뿐입니다.
- 실제 호출이 있는 셀은 실행 직전에 `announce`로 모델 호출과 EXA 호출 규모를 한 줄 알려 주고, 비용은 본인 키로 청구됩니다.
- 이 과정은 SDK 자동 재시도를 끕니다. 429 오류가 나면 1분쯤 기다렸다가 그 셀부터 다시 실행합니다.

## 셀 표지: 예측 · 관찰 · 실패 재현 · 직접 해보기 · 확인 질문

노트북마다 같은 표지가 붙어 있습니다. 결과를 눈으로 훑는 대신 자기 예측과 비교해 읽도록 만든 장치입니다.

| 표지 | 하는 일 | 쓰는 법 |
|---|---|---|
| `**먼저 예측하세요.**` | 셀을 실행하기 전에 결과를 적게 합니다 | 출력이 어떨지 한 줄로 적고, 실행 후 맞았는지 봅니다 |

### 실행 규모를 정하는 두 스위치

기본값은 모두 `False`라서 위에서 아래로 한 번 실행해도 이 비용이 더해지지 않습니다. 시간 여유와 크레딧을 보고 직접 켭니다.

- **`RUN_EXERCISE`**: `직접 해보기`의 유료 칸 첫 줄에 있습니다. 칸마다 바꿀 값이 변수로 빼 있습니다. 값을 바꾼 뒤 `True`로 바꿔 그 칸만 실행합니다. 꺼져 있으면 "실행하지 않았습니다. 고친 뒤 True로 바꾸세요"를 출력합니다.
- **`RUN_OPTIONAL`**: 규모가 큰 선택 셀을 켭니다. 05는 첫 코드 셀에 있고(7절 전체 비교), 06은 `CONFIG` 셀에 있습니다(병렬을 한 번 더 돌려 같은 구조 안의 변동을 봅니다). 01~04에는 없습니다.

아래 표는 저자가 임시 사본에서 스위치를 `True`로만 바꾸고(바꿀 값은 기본값 그대로) 돌렸을 때 **그 칸들이 더한 호출**입니다. 기본 실행에서 0회였다가 켜서 호출이 생긴 셀만 셌습니다(`outputs/live/<노트북>.json`에서 0회였고 `<노트북>.exercises.json`에서 0회를 넘은 셀의 `model_calls`와 `seconds`).

| 노트북 | 켜는 것 | 더해진 모델 호출 | 더해진 초 | 더해진 EXA 호출 |
|---|---|---:|---:|---:|
| 01 | `RUN_EXERCISE` 유료 칸 2개 | 6 | 20.6 | 0 |
| 02 | `RUN_EXERCISE` 유료 칸 2개 | 18 | 52.4 | 0 |
| 03 | `RUN_EXERCISE` 유료 칸 1개 | 6 | 12.5 | 0 |
| 04 | `RUN_EXERCISE` 유료 칸 1개 | 2 | 4.5 | 0 |
| 05 | `RUN_OPTIONAL` (전체 비교) | 265 | 694.7 | 0 |
| 05 | `RUN_EXERCISE` 유료 칸 3개 | 51 | 144.3 | 0 |
| 06 | `RUN_OPTIONAL` (병렬 한 번 더) | 7 | 43.5 | 6 |
| 06 | `RUN_EXERCISE` 유료 칸 3개 | 28 | 166.4 | 20 |

- 06의 EXA 호출은 `outputs/live/06-Lab-Research-Agents.exercises.executed.ipynb`의 셀 출력에서 읽었습니다(`*.json`에는 EXA 칸이 없습니다).
- "더해진 초"는 칸별 초를 반올림 전 값으로 더한 뒤 한 자리로 맞춘 값입니다. 이번 값에서는 02와 06 `RUN_EXERCISE` 두 행이 반올림한 칸별 값을 더한 것과 다릅니다. 02는 반올림한 30.6과 21.9를 더하면 52.5이지만 반올림 전 값 30.574와 21.859를 더하면 52.433이라서 52.4로, 06은 30.7, 96.6, 39.2를 더하면 166.5이지만 30.682, 96.553, 39.198을 더하면 166.433이라서 166.4로 적었습니다. 나머지 행은 어느 쪽으로 더해도 같습니다(예: 01의 두 칸은 4.4와 16.2로 20.6).
- 각 칸이 `announce`로 알리는 모델 호출 수는 그 칸의 상한이고, 저자 실행 13개(`.exercises` 포함)에서 모델을 부른 98개 칸은 모두 고지에 `model_calls=` 숫자가 있어 실측과 비교됐고, 자기 고지를 넘은 칸은 없습니다. 저자 감사(`tests/audit_live.py`)는 고지를 넘은 칸뿐 아니라 고지에 모델 호출 숫자가 없어 비교할 수 없는 칸과 실행본이 없는 기록도 실패로 봅니다. 넘은 실행은 감사가 실패시켰고 고지를 고쳐 다시 돌렸으므로, 남긴 기록은 모두 감사를 통과한 것입니다. 이력이 하나 있습니다. 05를 처음 돌렸을 때 한 칸(`hybrid 단순 사례와 복합 사례`)이 22회를 불러 고지 20회를 넘었고, 고지를 30회로 고쳐 다시 돌렸습니다. 지금 남은 05 기록은 2026-11-03에 다시 돌린 것이고 이 칸은 기본 실행 16회, `.exercises` 14회입니다. 그래도 모델이 도구를 몇 번 부르는지는 실행마다 달라서 수강생 환경에서는 넘을 수 있으니, 출력의 집계도 함께 봅니다. 켜기 전에 규모를 가늠하려면 이 표의 실측을 보세요.
- 같은 질문도 실행마다 다르게 끝날 수 있습니다. 모델이 어떤 도구를 몇 번 부르고 어디서 멈추는지가 매번 달라서, 한 번의 결과를 결론으로 삼지 않고 "1회 관찰"로 읽습니다. 같은 조건을 3회 이상 반복하기 전에는 평균이나 우열을 말하지 않습니다.

## 실측 비용

아래 표는 저장소 루트에서 다음 명령(`cost_report`)을 실행한 결과입니다. 한 번 실행한 기록(`outputs/live/*.usage.jsonl`)에서 모델 호출 수와 토큰을 읽고, 비용은 그 기록에 남은 모델(`claude-sonnet-5-5`)의 단가로 계산합니다.

```bash
uv run --no-sync python Day03_new/tests/cost_report.py
```

실행 기록은 두 종류로 나누어 읽습니다. 이름 끝에 `.exercises`가 붙은 것은 임시 사본에서 `RUN_EXERCISE`와 `RUN_OPTIONAL`을 모두 `True`로 바꿔 노트북 **전체를 처음부터 다시 돌린** 실행입니다. 기본 실행에 해보기 몫만 얹은 것이 아니고, 기본 칸도 그 실행에서 새로 돌았으므로 두 표를 더하지 않습니다.

모든 실행이 `finished: true`, 오류 0건으로 끝났고, 표의 호출 수·토큰은 각 `*.json`의 값과 일치합니다. 명령 출력 맨 아래의 합계(1022회, 3357.1초, 7.1327달러)는 기본 실행과 `.exercises` 실행을 모두 더한 값이라 아래 두 표의 합계와 다릅니다. 두 실행은 겹치므로 그렇게 더하지 않습니다. 아래 합계는 행마다 반올림하기 전 값을 더해 맞춘 것이라, 표에 보이는 행을 그대로 더하면 끝자리가 어긋날 수 있습니다(이번 값에서는 `.exercises` 표의 초 한 칸만 어긋납니다. 행의 초를 더하면 2242.9로 합계 2242.8과 0.1 어긋나고, 나머지 칸은 두 표 모두 행을 더해도 같습니다).

- **한 번 실행한 값이고 한 대의 컴퓨터에서 쟀습니다**(1회 관찰, 1대). 평균이나 보장이 아닙니다. 같은 모델이 같은 코드를 돌려도 호출 수가 달라집니다. 같은 노트북의 기본 실행과 `.exercises` 실행에서 **둘 다 유료로 돈 같은 셀들**만 합치면 01은 45회와 45회, 02는 33회와 35회, 03은 38회와 38회, 04는 35회와 34회, 05는 142회와 135회, 06은 28회와 28회였습니다. 견준 것은 노트북마다 위 두 표의 같은 이름 한 쌍이고, 모두 같은 코드로 돌린 기록입니다(아래 "기록의 시점"). 모두 기본 실행 직후에 `.exercises`를 돌렸습니다. 칸별로도 다릅니다. 05의 `hybrid 단순 사례와 복합 사례` 칸은 16회와 14회였습니다.
- **기록의 시점: 모두 같은 코드입니다.** 13개 기록은 모두 프레임워크가 자동으로 붙이는 `general-purpose` 하위 에이전트를 끈 뒤, 2026-11-03 00:05~01:03(한국 시간. 협정세계시로는 2026-11-02)에 지금 코드(`mas_lab`, 2026-11-02 09:13에 `Day02_new`와 맞춘 `rag_lab`, 지금 노트북)로 하나씩 차례로 다시 돌린 것입니다. 이전 기록은 `outputs/live/superseded-20261102-before-subagent-off/`에 남겨 두었고, 그보다 앞선 기록은 `outputs/live/superseded-20261102-before-full-rerun/`(12개)과 `outputs/live/superseded-20261102/`(02 기본 실행)에 있으며, 모두 위 표에는 들어 있지 않습니다.
  - 이번 재실행 경위와 이전 기록과의 비교는 `docs/audit/live-rerun-20261102b-notes.md`에, 직전 재실행은 `docs/audit/live-rerun-20261102-notes.md`에, 그 전의 판단 근거(고치기 전후 비교, 동기화 앞뒤의 검색 비교)는 `docs/audit/stale-records-notes.md`, `docs/audit/replay-4-notes.md`, `docs/audit/sync-equivalence-notes.md`에 있습니다.
- "초"는 그 컴퓨터에서 노트북이 돈 기계 시간일 뿐입니다. 읽고 예측하고 해보기를 하는 시간은 들어 있지 않습니다. 시간표의 60분은 설계값이며, 이 폴더에 사람이 직접 따라 하며 시간을 잰 리허설 기록은 없습니다.
- 단가(100만 토큰당)는 Anthropic 1차 API 요금(2026-10 기준) `claude-sonnet-5-5` 입력 $2, 출력 $10, 캐시 읽기 $0.2입니다. 기록된 입력 토큰에는 캐시 읽기가 들어 있어 캐시 읽기분은 캐시 단가로, 나머지는 입력 단가로 계산합니다(기본 실행의 캐시 읽기 토큰은 804,581개, `.exercises`는 1,822,833개). 모델이나 effort를 바꾸면 값이 달라지며 위 명령이 그 기록으로 다시 계산합니다.

## 채점은 없습니다

이 과정에는 채점하는 과제가 없습니다. 모든 코드가 완성되어 있고, 수강생은 실행하고 읽고 바꿔 봅니다. `직접 해보기`와 확인 질문은 자기 결과를 자기 말로 설명해 보기 위한 것입니다. 06 실습도 점수를 매기지 않고, 실패한 기록도 그 실습의 결과입니다. 잘 나온 반복만 남기거나 실패한 행을 지우지 않습니다. 자동 검사 표의 `False`는 점수가 아니라 "어디서 어긋났는지 읽을 단서"입니다. 자동 검사는 문자열 포함 검사라서 맞는 답도 `False`가 될 수 있습니다. 예를 들어 신청 기한을 `2026-09-20`이나 `9/20`으로 쓰면 정답표가 받는 `9월20일`, `다음달20일`과 달라서 `필수 사실` 칸이 실패합니다. 이것은 01·04·05가 일부러 읽게 하는 한계이고 05의 `CORRECT_BUT_FAILS` 셀이 이 실패에 기대고 있으므로, 정답표를 고쳐 통과시키지 않고 답 본문을 원문과 사람이 대조합니다.
